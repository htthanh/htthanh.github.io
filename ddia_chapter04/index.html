Application thay đổi → data cũng thay đổi

Chapter 1: hãy xây hệ thống dễ thích nghi với thay đổi — evolvability. Thêm feature thường kéo theo thay đổi data: thêm field, thêm record type, trình bày data theo cách mới.

RELATIONAL

Mọi data tuân theo một schema. Có thể đổi bằng schema migration (ALTER), nhưng tại mỗi thời điểm chỉ có đúng một schema.

SCHEMA-ON-READ

“Schemaless” DB không enforce schema → chứa lẫn data format cũ và mới, ghi ở các thời điểm khác nhau.

Ở app lớn, thay đổi code không thể xảy ra tức thì. Old/new code và old/new data format sẽ cùng tồn tại trong hệ thống.

04

Language-Specific Formats

Java · java.io.SerializableRuby · MarshalPython · pickleKryo (3rd-party, Java)

Rất tiện: lưu và khôi phục in-memory object với rất ít code. Nhưng có những vấn đề sâu xa:

🔒

Language lock-in

Gắn chặt với một ngôn ngữ — đọc bằng ngôn ngữ khác rất khó. Khó tích hợp với hệ thống của tổ chức khác.

☠️

Security

Decode phải instantiate arbitrary classes. Attacker gửi byte sequence tùy ý → có thể dẫn tới remote code execution.

🧬

Versioning

Thường là “afterthought”: bỏ qua bài toán forward & backward compatibility.

🐢

Efficiency

CPU time và kích thước encoding cũng là afterthought. Java built-in serialization nổi tiếng chậm và bloated.

⇒ Dùng built-in encoding của ngôn ngữ cho bất cứ thứ gì ngoài mục đích rất tạm thời (transient) nhìn chung là một ý tồi.
05

JSON, XML & CSV: textual formats

Chuẩn hóa, nhiều ngôn ngữ đọc/ghi được, khá human-readable — “widely known, widely supported, and almost as widely disliked”. Nhưng có những vấn đề tinh tế:

🔢 Ambiguity về numbers

XML/CSV: không phân biệt number và string toàn chữ số. JSON: phân biệt string/number nhưng không phân biệt integer vs floating-point, không quy định precision.

> JSON.parse('{"id": 9007199254740993}').id …

Integer > 253 không biểu diễn chính xác được bằng IEEE 754 double.

Nhấn → để chạy từng bước.

🧱 Binary strings

JSON/XML hỗ trợ Unicode tốt nhưng không có binary string → phải encode Base64: hacky và tăng size 33%.

📐 Optional schema

XML Schema, JSON Schema rất mạnh nhưng phức tạp. Nhiều tool JSON không dùng schema → phải hardcode logic encode/decode.

📄 CSV

Không có schema; app tự định nghĩa ý nghĩa row/column. Format mơ hồ (value chứa dấu phẩy, newline?) — nhiều parser escape sai.

Dù vậy vẫn đủ tốt cho rất nhiều mục đích, nhất là data interchange giữa các tổ chức: khó nhất là khiến các tổ chức đồng ý với nhau về bất cứ thứ gì.

09

Field tags & schema evolution

Encoded record = nối các field đã encode. Mỗi field nhận diện bằng tag number + datatype annotation; field không set thì bị bỏ qua. ⇒ Đổi tên field được (data không chứa tên), nhưng không được đổi tag.

schema v1 old

1: userName2: favoriteNumber3: interests

schema v2 new

1: userName2: favoriteNumber3: interests4: photoURL

Nhấn → để chạy từng bước.

FORWARD COMPAT

Old code đọc record do new code ghi: tag lạ ⇒ ignore.

BACKWARD COMPAT

Mọi field thêm sau lần deploy đầu tiên phải là optional hoặc có default value.

REMOVE FIELD

Không xoá được field required. Tag cũ có thể vẫn nằm trong data đâu đó → new code phải ignore nó.

protobuf: repeated

Không có list/array datatype; có marker repeated (cạnh required/optional): cùng tag xuất hiện nhiều lần.

⇒ Đổi optional (single-valued) thành repeated (multi-valued) là OK: new code đọc data cũ thấy list 0 hoặc 1 phần tử; old code đọc data mới chỉ thấy phần tử cuối.

Thrift: list<T>

Có list datatype riêng, parameterized theo element type. Không evolve single → multi-valued được như protobuf, nhưng hỗ trợ nested lists.

Schema evolution rules trong Avro

FORWARD

writer = new schema

writer = old schema

Thay đổiHệ quả

🚫 null không phải default

Muốn field nullable phải dùng union type: union { null, long, string } field;. Chỉ dùng null làm default nếu nó là một branch của union (chính xác: branch đầu tiên).

Không có optional / required

Avro dùng union types + default values thay vì marker như protobuf/Thrift. Dài dòng hơn, nhưng tường minh về cái gì được null ⇒ ngăn bug.

Đổi datatype

Được, nếu Avro convert được kiểu đó.

11

Nhưng reader lấy writer’s schema ở đâu?

Không thể nhét cả schema vào mỗi record — schema thường lớn hơn data, mất hết lợi ích của binary encoding. Câu trả lời tùy ngữ cảnh:

🗃️

Large file, nhiều records

Phổ biến với Hadoop: hàng triệu record cùng một schema → ghi writer’s schema một lần ở đầu file. Avro có format riêng: object container files.

🗄️

Database, records ghi riêng lẻ

Mỗi record có thể ghi bằng schema khác nhau → thêm version number ở đầu mỗi record, lưu danh sách schema versions trong DB. (Espresso của LinkedIn làm vậy.)

🔌

Gửi qua network connection

Hai process negotiate schema version khi setup connection, dùng suốt lifetime của connection. Avro RPC hoạt động như vậy.

Một database of schema versions luôn hữu ích: vừa là documentation, vừa cho phép check compatibility trước khi deploy. Version number: integer tăng dần, hoặc hash của schema.

Code generation & dynamically typed languages

STATICALLY TYPED

Java, C++, C#

Code generation từ schema rất hữu ích: in-memory structure hiệu quả cho data đã decode, type checking và autocompletion trong IDE.

DYNAMICALLY TYPED

JavaScript, Ruby, Python

Không có compile-time type checker để thỏa mãn → generate code ít ý nghĩa, thường bị “frowned upon” vì thêm bước compile. Với dynamically generated schema, code generation là vật cản không cần thiết.

13

The Merits of Schemas

Schema language của protobuf/Thrift/Avro đơn giản hơn nhiều so với XML Schema / JSON Schema (vốn hỗ trợ validation như regex, range 0–100) → dễ implement, hỗ trợ nhiều ngôn ngữ.

📜 Ý tưởng không mới: ASN.1

Chuẩn hóa từ 1984; binary encoding DER vẫn dùng cho SSL certificates (X.509). Cũng evolve bằng tag numbers — nhưng rất phức tạp, tài liệu kém.

Nhiều data system cũng có proprietary binary encoding: network protocol của relational DB, driver (ODBC/JDBC) decode thành in-memory structures.

📉 Compact hơn

Bỏ được field names khỏi encoded data — gọn hơn các “binary JSON”.

📘 Documentation luôn đúng

Schema bắt buộc để decode ⇒ chắc chắn up to date (docs viết tay thì dễ lệch thực tế).

✅ Check compatibility trước khi deploy

Giữ database of schemas để kiểm tra forward/backward compatibility.

🧰 Code generation

Type checking lúc compile cho statically typed languages.

Schema evolution cho sự linh hoạt như schemaless/schema-on-read JSON DB, đồng thời cho guarantees tốt hơn về data và tooling tốt hơn.
14

Modes of Dataflow

Gửi data cho một process không share memory ⇒ phải encode thành bytes. Compatibility là quan hệ giữa process encode và process decode. Vậy ai encode, ai decode?

🗄️

Via databases

Process ghi DB encode, process đọc DB decode.

🔁

Via service calls

REST & RPC: client encode request, server decode request rồi encode response, client decode response.

📨

Via async message passing

Message brokers & actors: sender encode, recipient decode.

Evolvability = upgrade từng phần của hệ thống độc lập, không phải đổi mọi thứ cùng lúc.

Data outlives code

Trong cùng một DB có value ghi 5 ms trước và value ghi 5 năm trước. Deploy version mới thay code cũ trong vài phút — nhưng data 5 năm tuổi vẫn nằm đó với encoding gốc.

● schema v1 (cũ)● schema mới

Nhấn → để chạy từng bước.

Schema change không rewrite

Phần lớn relational DB cho phép thêm column với default null mà không rewrite data; khi đọc row cũ, DB điền null cho column thiếu (MySQL là ngoại lệ hay rewrite cả table). Espresso dùng Avro để tận dụng evolution rules.

⇒ Schema evolution khiến cả DB trông như được encode bằng một schema duy nhất, dù storage chứa nhiều version lịch sử.

🧊 Archival storage

Snapshot cho backup hoặc data warehouse: encode nhất quán bằng schema mới nhất. Dump ghi một lần, immutable → hợp với Avro object container files, hoặc column-oriented như Parquet.

Dataflow Through Services: REST & RPC

Hai vai trò: clients và servers. Server expose một API qua network — gọi là service. Web: browser gửi GET/POST; native app, hay JavaScript app dùng XMLHttpRequest (Ajax) nhận JSON.

Service ≈ database có giới hạn

DB cho phép arbitrary queries; service chỉ expose API theo business logic ⇒ encapsulation, kiểm soát chặt client được làm gì.

SOA / microservices: mỗi service do một team sở hữu, deploy & evolve độc lập ⇒ old/new version của server và client chạy cùng lúc ⇒ encoding phải compatible qua các version của API.

15

Web services: REST vs SOAP

Hai triết lý gần như đối lập — và thường là chủ đề tranh cãi nảy lửa.

REST

Design philosophy, không phải protocol

  • Xây trên nguyên lý của HTTP: URL định danh resources; dùng HTTP features cho cache control, authentication, content type negotiation.
  • Data format đơn giản; gắn với microservices, phổ biến cho cross-organizational integration.
  • API theo REST = RESTful. Mô tả bằng OpenAPI (Swagger).
SOAP

XML-based protocol

  • Muốn độc lập với HTTP, tránh dùng HTTP features; kèm cả “hệ sinh thái” chuẩn phức tạp WS-*.
  • API mô tả bằng WSDL → code generation; không human-readable ⇒ phụ thuộc nặng vào tooling, IDE.
  • Interoperability giữa các vendor hay có vấn đề → vẫn dùng ở enterprise lớn, nhưng hết thời ở công ty nhỏ.
Lưu ý: SOAP không bắt buộc cho SOA. SOAP là một technology cụ thể; SOA là cách tiếp cận chung để xây hệ thống.

The problems with RPC

Remote procedure call (từ 1970s) cố làm request tới remote service trông giống gọi function local — abstraction gọi là location transparency.

EJBJava RMIDCOMCORBA

EJB/RMI chỉ cho Java, DCOM chỉ cho Microsoft, CORBA quá phức tạp và không có backward/forward compatibility.

Cách tiếp cận này fundamentally flawed: network request khác hẳn local function call.

PredictabilityThành/bại tùy tham số bạn kiểm soátRequest/response có thể mất, máy remote chậm/chết — ngoài tầm kiểm soát

Current directions for RPC

RPC không biến mất. Thế hệ framework mới thừa nhận remote request khác local call:

gRPC

RPC trên Protocol Buffers. Hỗ trợ streams: một call là chuỗi request và response theo thời gian.

Finagle

Dùng Thrift; futures (promises) bọc async action có thể fail, dễ gọi song song nhiều service và gộp kết quả.

Rest.li

JSON over HTTP, cũng dùng futures.

Thrift · Avro RPC

Message-Passing Dataflow

Nằm giữa RPC và databases: như RPC — message tới process khác với low latency; như DB — không đi qua connection trực tiếp mà qua message broker (message queue, message-oriented middleware) lưu tạm message.

Ưu điểm so với direct RPC

  • Làm buffer khi recipient unavailable/overloaded → reliability.
  • Tự redeliver message cho process đã crash → không mất message.
  • Sender không cần biết IP + port của recipient (cloud: VM đến rồi đi).
  • Một message gửi tới nhiều recipients.
  • Decouple sender và recipient: chỉ publish, không quan tâm ai consume.

Distributed actor frameworks

Actor model: programming model cho concurrency trong một process. Thay vì threads (race conditions, locking, deadlock), logic nằm trong actors — mỗi actor có local state riêng, giao tiếp bằng asynchronous messages, xử lý một message một lúc. Message delivery không được đảm bảo.

Distributed: cùng cơ chế message-passing dù sender/recipient cùng node hay khác node. Location transparency hợp với actor model hơn RPC, vì actor model vốn đã giả định message có thể mất.

Rolling upgrade vẫn cần forward & backward compatibility: message có thể đi từ node mới sang node cũ và ngược lại.

Akka

Mặc định dùng Java built-in serialization — không forward/backward compat. Thay bằng Protocol Buffers ⇒ rolling upgrade được.

Orleans

Custom encoding mặc định không hỗ trợ rolling upgrade: phải dựng cluster mới, chuyển traffic, tắt cluster cũ. Có custom serialization plug-ins.

Erlang OTP

Đổi record schema khó bất ngờ; rolling upgrade được nhưng phải lên kế hoạch kỹ. maps datatype (R17, 2014) có thể giúp.

Tóm tắt Chapter 4

Rolling upgrades cho phép release không downtime và ít rủi ro ⇒ mọi data trong hệ thống cần backward (new code đọc old data) và forward (old code đọc new data) compatibility.

🔒 Language-specific

Bó buộc một ngôn ngữ, thường không có forward/backward compatibility.

📝 JSON · XML · CSV

Phổ biến; compatibility tùy cách dùng. Schema optional; mơ hồ về numbers và binary strings.

⚡ Thrift · protobuf · Avro

Compact, compatibility semantics rõ ràng, schema = docs + code gen. Nhược điểm: phải decode mới đọc được.
