PART III

Derived Data

Trong thực tế, một ứng dụng lớn thường phải tích hợp nhiều data system khác nhau (database, cache, search index, analytics…). Part III bàn về cách ghép chúng lại thành một kiến trúc coherent.

SYSTEMS OF RECORD

Source of truth

Giữ phiên bản authoritative của data. Data mới được ghi vào đây đầu tiên; mỗi fact được biểu diễn đúng một lần (thường là normalized). Nếu có khác biệt giữa các hệ thống, system of record là đúng.

DERIVED DATA SYSTEMS

Kết quả của một transformation

Lấy data có sẵn rồi transform/process theo cách nào đó. Mất thì tạo lại được từ source. Ví dụ: cache, denormalized values, indexes, materialized views, recommendation model.

Chain of commands vs custom program

Cùng bài toán, viết bằng Ruby
1counts = Hash.new(0)
2File.open('/var/log/nginx/access.log') do |file|
3 file.each do |line|
4 url = line.split[6]
5 counts[url] += 1
6 end
7end
8top5 = counts.map{|url, count| [count, url] }
9 .sort.reverse[0...5]
10top5.each{|count, url| puts "#{count} #{url}" }

Không gọn bằng Unix pipes nhưng dễ đọc. Khác biệt lớn không nằm ở syntax mà ở execution flow khi chạy trên file lớn.

Nguyên lý giống SSTables & LSM-Trees (Chapter 3): sort chunk trong memory → ghi segment files ra disk → merge thành file lớn. Mergesort có access pattern sequential, rất hợp với disk.
IN-MEMORY AGGREGATION · Ruby

Giữ hash table URL → counter. Working set (lượng memory cần random access) chỉ phụ thuộc vào số URL khác nhau: 1 triệu dòng cùng một URL vẫn chỉ tốn 1 entry. Website nhỏ/vừa: vừa trong ~1 GB RAM → chạy tốt ngay trên laptop.

SORTING · Unix pipeline

Không có hash table; dựa vào việc sort danh sách URL để các bản lặp đứng cạnh nhau. Khi working set lớn hơn memory, cách này tận dụng disk hiệu quả.

🐧 GNU Coreutils sort

Tự động spill to disk khi dataset lớn hơn memory, và tự parallelize sort trên nhiều CPU cores → chuỗi lệnh Unix đơn giản vẫn scale tốt. Bottleneck thường là tốc độ đọc file từ disk.

04

The Unix Philosophy

“We should have some ways of connecting programs like [a] garden hose—screw in another segment when it becomes necessary to massage data in another way. This is the way of I/O also.” — Doug McIlroy, cha đẻ Unix pipes (1964)
🎯

Do one thing well

Mỗi program làm tốt một việc. Việc mới → viết program mới, đừng nhồi thêm “features” vào program cũ.

🔗

Output = input

Output của mọi program sẽ thành input của một program khác chưa biết trước. Đừng xả thông tin thừa, tránh format cột cứng nhắc hay binary, đừng đòi interactive input.

⚡

Try early

Thiết kế và build để dùng thử sớm, lý tưởng trong vài tuần. Đừng ngại vứt bỏ phần vụng về và build lại.

🧰

Build tools

Dùng tools thay cho sức người để nhẹ việc lập trình, kể cả khi phải đi đường vòng để viết tool rồi bỏ đi sau đó.

Automation, rapid prototyping, incremental iteration, thân thiện với experimentation, chia dự án lớn thành phần nhỏ — nghe rất giống Agile và DevOps ngày nay. Bốn thập kỷ, thay đổi ít đến bất ngờ. Ví dụ: sort tốt hơn sort trong standard library của đa số ngôn ngữ, nhưng chỉ thật sự mạnh khi kết hợp với uniq.
04b

Uniform interface & separation of logic and wiring

🔌 A uniform interface

Muốn nối output của bất kỳ program nào vào input của program khác → tất cả phải dùng cùng một I/O interface. Trong Unix, đó là file (chính xác hơn: file descriptor) — một chuỗi bytes có thứ tự.

📄 file trên filesystem🔁 pipe · stdin · stdout🌐 TCP socket🔊 /dev/audio · /dev/lp0
↓ cùng một interface: ordered sequence of bytes

Quy ước: nhiều tool coi bytes là ASCII text, record phân tách bằng \n. Không hoàn hảo ({print $7} khó đọc), nhưng hiếm phần mềm nào compose tốt như Unix tools. Thiếu tích hợp giữa các hệ thống → Balkanization of data.

🧵 Separation of logic and wiring

Program chỉ đọc stdin, ghi stdout; không quan tâm data đến từ đâu, đi về đâu. Shell user tự “đi dây”.

stdin→
program logic
không biết file path
→stdout
wiring: chưa nối

Nhấn → để chạy từng bước.

Đây là dạng loose coupling, late binding, inversion of control. Giới hạn: program cần nhiều input/output thì khó; không thể pipe output vào network connection; program tự mở file/network thì mất sự linh hoạt của việc đi dây trong shell.

05

MapReduce & Distributed Filesystems · HDFS

Một MapReduce job giống một Unix process: nhận một hoặc nhiều input, sinh một hoặc nhiều output, không sửa input, không có side effect nào ngoài output. Thay vì stdin/stdout, nó đọc/ghi file trên distributed filesystem.

  • HDFS (Hadoop Distributed File System) — bản open source của Google File System (GFS).
  • Khác: GlusterFS, QFS; object storage như Amazon S3, Azure Blob Storage, OpenStack Swift.
  • Shared-nothing, khác với shared-disk (NAS, SAN) cần hardware chuyên dụng, Fibre Channel.

Nhấn → để chạy từng bước.

Deployment HDFS lớn nhất: hàng chục nghìn máy, tổng dung lượng hàng trăm petabytes — rẻ hơn nhiều so với storage appliance chuyên dụng nhờ commodity hardware + open source.
06

MapReduce Job Execution

Pattern xử lý của MapReduce gần như trùng khớp với ví dụ log analysis:

#MapReduceUnix pipeline
1Đọc input files, tách thành records input format parser\n là record separator
2Gọi mapper để extract key & value your codeawk '{print $7}' → key = URL
3Sort tất cả key-value pairs theo key implicitsort lần thứ nhất
4Gọi reducer lặp qua các pairs đã sort your codeuniq -c
Cần sort lần hai (xếp hạng URL)? Viết MapReduce job thứ hai lấy output của job đầu làm input. Mapper chuẩn bị data cho việc sort; reducer xử lý data đã được sort.
🗺️ Mapper

Gọi một lần cho mỗi input record, extract key-value (có thể 0, 1 hoặc nhiều pair). Stateless: không giữ state giữa các record → mỗi record xử lý độc lập.

🧮 Reducer

Framework gom mọi value có cùng key, gọi reducer với iterator qua tập value đó. Reducer sinh output records (vd. số lần một URL xuất hiện).

☕ Implementations

Hadoop: mapper/reducer là Java class. MongoDB, CouchDB: JavaScript functions. Có thể dùng cả Unix tools làm mapper/reducer.

07

Distributed execution · the shuffle

Khác biệt chính so với Unix pipes: MapReduce parallelize trên nhiều máy mà bạn không cần viết code xử lý parallelism. Parallelization dựa trên partitioning (Chapter 6).

Nhấn → để chạy từng bước.

Shuffle = partition theo reducer + sort + copy partitions từ mapper sang reducer. Tên dễ gây nhầm: khác với xáo bài, không có gì random ở đây.

Mục tiêu ví dụ: trang nào phổ biến với nhóm tuổi nào? Event chỉ có user ID, nhúng cả profile vào mọi event thì quá lãng phí → cần join. (Một phần của star schema.)

CÁCH NGÂY THƠ

Duyệt từng event, query database từ xa cho mỗi user ID:

  • Throughput bị giới hạn bởi round-trip time tới DB server
  • Local cache hiệu quả hay không phụ thuộc phân bố data
  • Nhiều query song song dễ overwhelm database
  • Job trở nên nondeterministic vì data từ xa có thể thay đổi
CÁCH TỐT HƠN

Lấy bản copy của user database (vd. từ backup qua ETL), đặt vào cùng HDFS với activity log. Rồi dùng MapReduce gom các record liên quan về cùng một chỗ. Computation càng local trên một máy càng tốt.

11

Bringing related data together · GROUP BY

📮 Key như một địa chỉ

Có thể xem mapper đang “send messages” tới reducer: key đóng vai destination address. Không phải IP/port, nhưng mọi pair cùng key được giao tới cùng một đích (một lần gọi reducer).

Tách network khỏi application logic

MapReduce tách phần đưa data tới đúng máy khỏi phần xử lý data. Khác với cách dùng DB thông thường, nơi request fetch data nằm sâu trong application code. Framework còn che partial failures: tự retry task lỗi mà không ảnh hưởng logic.

🧺 GROUP BY

Cấu hình mapper sao cho key = grouping key; partition + sort sẽ gom cùng key về cùng reducer. Grouping và join trông rất giống nhau trên MapReduce.

COUNT(*) — đếm records mỗi group (như page views)
SUM(fieldname) — cộng giá trị một field
Top k records theo ranking function
Sessionization: gom mọi activity event của một user session (session cookie / user ID làm grouping key) để xem chuỗi hành động — dùng cho A/B testing hay đánh giá marketing. Events vốn nằm rải rác trên log của nhiều web server.

🐷 Pig · skewed join

Chạy sampling job trước để tìm hot keys. Khi join, mapper gửi record của hot key tới một reducer ngẫu nhiên trong vài reducer (thay vì chọn theo hash); input còn lại được replicate tới mọi reducer xử lý key đó.

🥣 Crunch · sharded join

Tương tự, nhưng hot keys phải được chỉ định tường minh thay vì sampling.

🐝 Hive · skewed join optimization

Hot keys khai báo trong table metadata, record của chúng lưu ở file riêng; khi join dùng map-side join cho hot keys.

Khi grouping/aggregate theo hot key: làm 2 stage. Stage 1 gửi record tới reducer ngẫu nhiên, mỗi reducer aggregate một phần; stage 2 gộp kết quả thành một value mỗi key.

Partitioned hash join · map-side merge join

🪣 Partitioned hash join (Hive: bucketed map join)

Nếu cả hai input được partition giống nhau — cùng key, cùng hash function, cùng số partition — áp dụng hash join cho từng partition độc lập. Ví dụ: chia theo chữ số cuối của user ID (10 partitions): mapper 3 chỉ load users có ID tận cùng là 3, rồi scan events của đúng những user đó.

users_*3partition 3
events_*3→ mapper 3

🔀 Map-side merge join

Input không chỉ partition giống nhau mà còn được sort theo cùng key → không cần vừa memory: mapper đọc tuần tự cả hai file theo thứ tự key tăng dần và match — đúng việc reducer thường làm.

🔎 Building search indexes

Mục đích ban đầu của MapReduce ở Google: build index cho search engine — một workflow 5–10 MapReduce jobs. (Hadoop MapReduce vẫn là cách tốt để build index cho Lucene/Solr.)

Mapper partition tập documents, mỗi reducer build index cho partition của mình, index files được ghi lên distributed filesystem → document-partitioned indexes parallelize rất tốt. Index files là immutable sau khi tạo.

14b

Key-value stores as batch process output

Batch job build ML systems (spam filter, anomaly detection, image recognition) và recommendation systems (people you may know, related products…). Output là một database mà web app cần query. Đưa nó về đó thế nào?

Ý TƯỞNG TỒI

Gọi DB client trong mapper/reducer, ghi từng record vào database production:

  • Network request mỗi record chậm hơn throughput batch nhiều orders of magnitude
  • Nhiều task song song cùng ghi → overwhelm database, ảnh hưởng query của hệ thống khác
  • Mất đảm bảo all-or-nothing: side effect của job chạy dở bị lộ ra ngoài; phải lo task attempts & speculative execution
GIẢI PHÁP TỐT

Build database mới tinh ngay trong batch job, ghi thành files trong output directory → immutable → bulk load vào server phục vụ read-only. Hỗ trợ: Voldemort, Terrapin, ElephantDB, HBase bulk loading. Read-only nên cấu trúc đơn giản, không cần WAL.

Philosophy of batch process outputs

Giống Unix: input không đổi, output cũ được thay hoàn toàn, không có side effect nào khác. Inputs immutable + tránh side effects → vừa nhanh vừa dễ maintain:

⏪ Human fault tolerance

Deploy code lỗi → output sai? Roll back code và chạy lại, hoặc chuyển về output cũ ở directory khác. Database read-write không làm được: rollback code không sửa được data đã ghi sai.

🚀 Minimizing irreversibility

Rollback dễ → phát triển feature nhanh hơn so với môi trường mà lỗi có thể gây thiệt hại không thể đảo ngược. Có lợi cho Agile.

🔁 Automatic retry an toàn

Task lỗi được re-schedule trên cùng input. Lỗi do bug → fail sau vài lần; lỗi transient → được tolerate. An toàn chỉ vì input immutable và output của task lỗi bị bỏ.

🧪 Reuse cùng input

Cùng một tập file dùng cho nhiều job, kể cả monitoring jobs so sánh output với lần chạy trước.

Separation of logic and wiring: một team viết job “do one thing well”, team khác quyết định chạy ở đâu, khi nào (input/output directories).
Khác Unix: thay vì untyped text (phải parse {print $7}), Hadoop dùng format có cấu trúc như Avro, Parquet — schema-based encoding, hỗ trợ schema evolution.
15

Comparing Hadoop to Distributed Databases

Hadoop ≈ một Unix phân tán: HDFS là filesystem, MapReduce là một Unix process “kỳ quặc” (luôn chạy sort giữa map và reduce). Các thuật toán join song song đã có trong MPP databases (Gamma, Teradata, Tandem NonStop SQL) từ hơn một thập kỷ trước. Khác biệt: MPP tập trung chạy analytic SQL; MapReduce + DFS giống một general-purpose OS chạy program tùy ý.

🗃️ Diversity of storage

Database bắt data theo một model cụ thể; file trên DFS chỉ là byte sequences: record, text, ảnh, video, sensor readings, feature vectors, genome… Hadoop cho phép dump data bừa bãi vào HDFS rồi tính cách xử lý sau; MPP cần modeling cẩn thận trước khi import.

🍣 sushi principle: “raw data is better”data lake · enterprise data hubschema-on-read

Làm data available nhanh thường giá trị hơn chọn data model lý tưởng từ đầu. Diễn giải data trở thành việc của consumer. Hadoop thường dùng cho ETL: dump raw → MapReduce làm sạch → import vào MPP warehouse.

⚙️ Diversity of processing models

MPP: monolithic, tích hợp chặt storage layout, query planning, scheduling, execution → performance rất tốt cho loại query được thiết kế; SQL dễ dùng cho tool như Tableau.

Nhưng ML, recommendation, full-text index với ranking, image analysis… cần viết code, không chỉ query. MapReduce cho phép chạy code tùy ý trên dataset lớn; có thể build SQL engine bên trên (Hive) và nhiều model khác.

Mọi processing model chạy trên một shared cluster, đọc cùng file trên DFS — không phải import data vào nhiều hệ thống chuyên biệt. HBase (OLTP) và Impala (MPP-style) đều dùng HDFS, không dùng MapReduce.

Nhưng máy hỏng đâu có thường xuyên? Lý do thật nằm ở môi trường Google: datacenter mixed-use, online services và batch chạy chung máy. Task có priority; task priority cao cần tài nguyên → task thấp hơn bị preempted.

Beyond MapReduce · Materialization of Intermediate State

MapReduce dễ hiểu nhưng không dễ dùng: viết job phức tạp bằng raw API rất cực (tự implement join). Pig, Hive, Cascading, Crunch giúp dễ viết hơn — nhưng vấn đề nằm ở execution model.

Output một job thường chỉ làm input cho một job khác cùng team → file trên DFS chỉ là intermediate state. Ghi nó ra file = materialization. Unix pipes thì stream qua buffer nhỏ.

🐢 Stragglers

Job chỉ bắt đầu khi mọi task của job trước xong; skew khiến vài task rất chậm kéo cả workflow.

♊ Mappers thừa

Mapper chỉ đọc lại file reducer vừa ghi để partition & sort lại — lẽ ra có thể gộp vào reducer trước.

Dataflow engines · Spark · Tez · Flink

Xử lý cả workflow như một job, thay vì nhiều subjob độc lập. Vẫn gọi user-defined function trên từng record, một thread, partition input, copy output qua network — nhưng các function (operators) không bị ép vào vai map/reduce xen kẽ.

Các cách nối operator → operator
🔀 Repartition + sort theo key (như shuffle) → sort-merge join, grouping
🪣 Partition giống nhau nhưng bỏ sort → partitioned hash join
📡 Gửi cùng output tới mọi partition → broadcast hash join

Dựa trên research systems Dryad, Nephele. Workflow viết bằng Pig, Hive, Cascading có thể chuyển từ MapReduce sang Tez/Spark chỉ bằng đổi config. Tez là library mỏng dựa trên YARN shuffle service; Spark, Flink là framework lớn có network layer, scheduler, API riêng.

✅ Ưu điểm so với MapReduce

  • Việc tốn kém như sorting chỉ làm ở chỗ thật sự cần
  • Không có map task thừa: việc của mapper gộp vào reduce operator trước
  • Joins & data dependencies khai báo tường minh → scheduler tối ưu locality (vd. trao đổi qua shared memory buffer)
  • Intermediate state giữ trong memory hoặc local disk, không ghi HDFS replicated
  • Operator chạy ngay khi input sẵn sàng, không chờ cả stage trước
  • Tái sử dụng JVM process, giảm startup overhead (MapReduce mở JVM mới mỗi task)
Spark/Flink/Tez sắp xếp operators thành một DAG (directed acyclic graph). Đừng nhầm với graph processing: ở đây flow giữa operator là graph, còn data là relational-style tuples.
18b

Fault tolerance & discussion of materialization

MAPREDUCE

Intermediate state materialized trên DFS là durable → task lỗi chỉ cần restart ở máy khác và đọc lại input.

SPARK · FLINK · TEZ

Không ghi intermediate state ra HDFS → máy hỏng thì recompute từ data còn lại (stage trước, hoặc input gốc trên HDFS). Framework phải nhớ data được tính thế nào:

Spark: RDD — track ancestryFlink: checkpoint operator state
Recompute không phải lúc nào cũng đúng: nếu intermediate data nhỏ hơn nhiều so với source, hoặc tính toán rất CPU-intensive, materialize ra file có thể rẻ hơn.

🎲 Determinism

Nếu data lỗi đã được gửi xuống downstream và lần recompute cho kết quả khác → downstream khó giải quyết mâu thuẫn; thường phải kill và chạy lại cả downstream. Tránh cascading faults: làm operators deterministic.

→ loại bỏ các nguồn nondeterminism, vd. dùng pseudorandom với fixed seed.

🚰 Pipelined execution

MapReduce ≈ ghi output mỗi lệnh ra temp file; dataflow engines ≈ Unix pipes (đặc biệt Flink). Riêng sorting buộc phải đọc hết input (record cuối có thể có key nhỏ nhất). Input đầu & output cuối vẫn thường nằm trên HDFS: input immutable, output thay hoàn toàn — chỉ bỏ được việc ghi intermediate state.

Graphs and Iterative Processing

Chapter 2 nhìn graph theo kiểu OLTP (query nhanh vài vertex). Batch context: xử lý/analyze toàn bộ graph — recommendation engines, ranking systems. Nổi tiếng nhất: PageRank, ước lượng độ phổ biến của web page dựa trên các trang link tới nó.

Nhiều graph algorithm duyệt từng edge một, join vertex với vertex kề để lan truyền thông tin, lặp đến khi xong (vd. transitive closure). Plain MapReduce chỉ chạy một pass → phải viết theo kiểu iterative:

① External scheduler chạy batch process tính một bước
② Kiểm tra điều kiện kết thúc: hết edge để đi? thay đổi < threshold?
③ Chưa xong → quay lại ① ↺
KÉM HIỆU QUẢ

MapReduce không hiểu bản chất iterative: luôn đọc toàn bộ input và ghi ra toàn bộ output mới, kể cả khi chỉ một phần nhỏ graph thay đổi.

19b

The Pregel processing model · BSP

Bulk synchronous parallel (BSP) — Apache Giraph, Spark GraphX, Flink Gelly; còn gọi là Pregel model (Google). Giống mapper “gửi message” tới reducer: một vertex gửi message tới vertex khác dọc theo edges.

  • Mỗi iteration, function được gọi cho từng vertex với các message gửi tới nó — như một lần gọi reducer.
  • Khác MapReduce: vertex nhớ state trong memory giữa các iteration → chỉ xử lý message mới. Không có message → không tốn công.
  • Giống actor model, nhưng state & message fault-tolerant, durable, giao tiếp theo round cố định.

🛟 Fault tolerance

Checkpoint state của mọi vertex cuối iteration. Node hỏng → roll back cả graph về checkpoint, hoặc (deterministic + logged messages) chỉ recover partition bị mất.

🧩 Parallel execution

“Thinking like a vertex”: graph thường partition theo vertex ID tùy ý → nhiều cross-machine traffic. Graph vừa một máy? Single-machine (kể cả GraphChi) thường thắng.

High-Level APIs and Languages

Infrastructure đã đủ robust để xử lý nhiều petabytes trên cluster >10,000 máy. Trọng tâm chuyển sang: programming model, hiệu năng xử lý, mở rộng loại bài toán giải được. Hive, Pig, Cascading, Crunch, và API riêng của Spark/Flink (lấy cảm hứng từ FlumeJava) dùng các building block relational-style: join, group by, filter, aggregate. Còn cho phép dùng interactive trong shell — rất “Unix philosophy”.

🧠

Declarative query languages

Khai báo join như relational operator → cost-based query optimizer (Hive, Spark, Flink) tự chọn join algorithm phù hợp và đổi thứ tự join để giảm intermediate state. Không cần nhớ hết các thuật toán join!

🏎️

Hiệu năng như MPP

Filter/map đơn giản viết declarative → đọc chỉ cột cần (column-oriented storage), vectorized execution (Hive, Spark DataFrames, Impala); Spark sinh JVM bytecode, Impala dùng LLVM. Vẫn giữ quyền chạy arbitrary code (libraries qua Maven, npm, Rubygems).

🎓

Specialization for domains

Reusable building blocks: ML (Mahout trên MapReduce/Spark/Flink, MADlib trong Apache HAWQ), spatial k-nearest neighbors, approximate search cho genome analysis.

Batch frameworks có thêm declarative operators, MPP databases ngày càng programmable — hai bên bắt đầu giống nhau: suy cho cùng, đều chỉ là systems for storing and processing data.

Tóm tắt Chapter 10

Triết lý Unix sống tiếp trong MapReduce và dataflow engines: inputs immutable, output thành input của program khác, giải bài toán lớn bằng cách compose các tool nhỏ “do one thing well”. Unix: files & pipes; MapReduce: distributed filesystem.

🧩 Partitioning

Mapper partition theo input block; output được repartition, sort, merge về các reducer partition để đưa data liên quan về cùng chỗ. Dataflow engines tránh sort khi không cần.

🛟 Fault tolerance

MapReduce ghi disk thường xuyên → recover task dễ nhưng chậm khi không lỗi. Dataflow engines giữ nhiều trong memory → recompute nhiều hơn; deterministic operators giảm phần phải tính lại.

🔗 Join algorithms

Sort-merge join (partition + sort + merge về một reducer call) · Broadcast hash join (input nhỏ load vào hash table ở mọi mapper) · Partitioned hash join (hai input partition giống nhau).

Programming model hạn chế có chủ đích (callbacks stateless, không side effect) cho phép framework retry an toàn và đảm bảo output như thể không có fault. Input của batch job là bounded → job biết khi nào xong. Chapter 11: input unbounded — stream processing.
