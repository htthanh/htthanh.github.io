PART II

Distributed Data

Đi từ một máy sang nhiều máy cùng tham gia lưu trữ & truy xuất data. Lý do: scalability, fault tolerance / high availability, latency (đặt data gần user).

SHARED-NOTHING ARCHITECTURE

Mỗi machine (node) dùng CPU, RAM, disk riêng; phối hợp qua network thông thường. Không cần hardware đặc biệt → có thể trải ra nhiều datacenter / region.

HAI CÁCH PHÂN TÁN DATA

Replication: cùng data, nhiều bản copy trên các node khác nhau (redundancy).
Partitioning (sharding): chia database lớn thành các phần nhỏ đặt ở các node khác nhau.

02

Leaders and Followers

· leader-based replication (active/passive, master–slave)

Mỗi node giữ một bản copy gọi là replica. Câu hỏi: làm sao đảm bảo mọi write tới được mọi replica?

  • Một replica là leader (master / primary). Mọi write từ client phải gửi tới leader; leader ghi vào local storage trước.
  • Các replica còn lại là followers (read replicas, slaves, secondaries, hot standbys). Leader gửi data change qua replication log / change stream; follower apply đúng thứ tự như leader.
  • Read: query leader hoặc bất kỳ follower. Nhưng từ góc nhìn client, followers là read-only.
Built-in trong PostgreSQL (9.0+), MySQL, Oracle Data Guard, SQL Server AlwaysOn; cả MongoDB, RethinkDB, Espresso; message brokers Kafka, RabbitMQ; thậm chí DRBD.

03

Synchronous vs Asynchronous Replication

Nhấn → để chạy từng bước.

SYNCHRONOUS

✓ Follower chắc chắn có bản up-to-date, consistent với leader.
✗ Follower không response (crash, network fault…) → write không xử lý được; leader phải block mọi write.

SEMI-SYNCHRONOUS

Không thể để tất cả followers sync. Thực tế: 1 follower sync, còn lại async → luôn có bản up-to-date trên ít nhất 2 node.

FULLY ASYNCHRONOUS

Leader vẫn xử lý write dù followers tụt lại. Nhưng leader chết không cứu được → write chưa replicate bị mất, dù đã confirm cho client (weakened durability). Vẫn rất phổ biến khi có nhiều followers / phân tán địa lý.

Research: chain replication — một biến thể sync, dùng trong Microsoft Azure Storage. Liên hệ consistency ↔ consensus: Chapter 9.

05

Handling Node Outages

· reboot từng node mà không downtime
FOLLOWER FAILURE · CATCH-UP RECOVERY

Mỗi follower giữ log các data change đã nhận trên local disk. Crash / restart / network gián đoạn → biết transaction cuối cùng đã xử lý → xin leader mọi change từ đó → caught up. Dễ.

LEADER FAILURE · FAILOVER

Khó hơn nhiều: promote một follower thành leader mới, reconfigure clients gửi write tới leader mới, các follower khác chuyển sang consume từ leader mới. Có thể manual hoặc automatic.

06

Failover is fraught with things that can go wrong

LOST WRITES

Với async replication, leader mới có thể chưa nhận đủ write của leader cũ. Leader cũ rejoin → các write chưa replicate thường bị discard → vi phạm kỳ vọng durability của client.

GITHUB INCIDENT

Một MySQL follower out-of-date được promote. Autoincrement counter tụt sau → reuse primary keys đã cấp. Key đó cũng dùng trong Redis → MySQL ↔ Redis inconsistent → private data lộ cho sai user.

SPLIT BRAIN

Hai node cùng tin mình là leader, cùng nhận write, không có conflict resolution → data mất / hỏng. Safety catch: fencing, a.k.a. STONITH (Shoot The Other Node In The Head) — thiết kế ẩu thì cả hai node bị tắt.

TIMEOUT BAO NHIÊU?

Dài → recovery lâu. Ngắn → failover không cần thiết: load spike hay network glitch làm response chậm vượt timeout. Hệ thống đang quá tải mà failover thêm thì càng tệ.

Không có easy solution → nhiều operations team failover thủ công dù software hỗ trợ automatic. Node failures, unreliable networks, trade-offs giữa consistency · durability · availability · latency là các vấn đề nền tảng của distributed systems (Chapter 8, 9).

NONDETERMINISTIC FUNCTIONS

NOW(), RAND() sinh giá trị khác nhau trên mỗi replica.

ORDER-DEPENDENT

Autoincrement hoặc phụ thuộc data hiện có (UPDATE … WHERE) → phải execute đúng cùng thứ tự trên mọi replica; khó khi nhiều transaction chạy concurrently.

SIDE EFFECTS

Triggers, stored procedures, UDFs có thể gây side effect khác nhau, trừ khi hoàn toàn deterministic.

Workaround: leader thay nondeterministic call bằng giá trị cố định. Nhưng quá nhiều edge cases. MySQL < 5.1 dùng; nay MySQL tự chuyển sang row-based nếu có nondeterminism. VoltDB dùng an toàn nhờ bắt transaction phải deterministic.

09

Problems with Replication Lag

· read-scaling architecture

Web thường read nhiều, write ít → thêm nhiều followers, phân tán read requests. Chỉ thực tế với asynchronous replication (sync tới tất cả thì một node chết là cả hệ thống không write được).

Eventual consistency

Đọc từ follower bị tụt → thấy data cũ. Query cùng lúc trên leader và follower cho kết quả khác nhau. Ngừng write và chờ → followers eventually bắt kịp.

Từ “eventually” cố ý mơ hồ: không có giới hạn replica có thể tụt bao xa. Bình thường replication lag chỉ vài phần giây; gần capacity hoặc network trục trặc → vài giây, thậm chí vài phút.

Reading Your Own Writes

· anomaly #1

Nhấn → để chạy từng bước.

READ-AFTER-WRITE CONSISTENCY

a.k.a. read-your-writes consistency: user reload trang thì luôn thấy update do chính mình submit.

KHÔNG HỨA GÌ VỀ NGƯỜI KHÁC

Update của user khác có thể hiện muộn hơn. Chỉ trấn an user rằng input của họ đã được lưu đúng.

Pattern phổ biến: data xem thường xuyên nhưng thỉnh thoảng mới write — write lên leader, read từ follower. Comment, record khách hàng, profile…
10b

Implement read-after-write consistency

👤 Đọc thứ user có thể sửa từ leader

Cần biết trước cái gì có thể đã bị sửa mà không query. Vd. social network: profile chỉ owner sửa → đọc profile của chính mình từ leader, profile người khác từ follower.

⏱️ Tiêu chí theo thời gian / lag

Nếu hầu hết mọi thứ đều editable thì cách trên mất read scaling. Thay vào đó: 1 phút sau update cuối → đọc từ leader; hoặc chặn query trên follower tụt > 1 phút.

🕓 Client nhớ timestamp write gần nhất

Replica phục vụ read phải reflect updates ít nhất tới timestamp đó; nếu chưa → chuyển replica khác hoặc chờ. Logical timestamp (vd. log sequence number) hoặc system clock (cần clock synchronization).

🌐 Nhiều datacenter

Request cần leader phải được route tới datacenter chứa leader → thêm complexity.

CROSS-DEVICE READ-AFTER-WRITE

Nhập trên laptop, xem trên điện thoại: timestamp “last update” phải centralized (device này không biết device kia đã write gì); và 2 device có network route khác nhau (home broadband vs cellular) → có thể phải route mọi device của một user tới cùng datacenter.

CONSISTENT PREFIX READS

Nếu một chuỗi write xảy ra theo thứ tự nào đó, ai đọc cũng thấy chúng theo đúng thứ tự đó.

VẤN ĐỀ CỦA PARTITIONED DATABASES

Các partition hoạt động độc lập → không có global ordering. Giải pháp: write có quan hệ nhân quả → cùng partition; hoặc thuật toán track causal dependencies (happens-before, cuối chương).

Tự hỏi

Nếu lag tăng lên vài phút, thậm chí vài giờ, app sẽ cư xử ra sao? “No problem” thì tốt. Nếu UX tệ → cần guarantee mạnh hơn. Giả vờ replication là synchronous trong khi nó asynchronous là công thức cho rắc rối về sau.

Transactions

Xử lý trong application code thì phức tạp, dễ sai. Tốt hơn: database “do the right thing” — đó là lý do transactions tồn tại. Nhiều distributed DB đã bỏ chúng vì cho là quá đắt; “eventual consistency là tất yếu” là quá đơn giản hoá (Chapter 7, 9, Part III).

14

Multi-Leader Replication

· master–master, active/active

Downside lớn của leader-based: chỉ một leader, mọi write phải qua nó. Không kết nối được leader → không write được.

Ý tưởng

Cho nhiều node nhận write. Node nào xử lý write thì forward change tới mọi node khác. Mỗi leader đồng thời là follower của các leader khác.

Use case #1: multi-datacenter operation

Mỗi datacenter một leader. Trong DC: leader–follower bình thường; giữa các DC: leader replicate sang leader khác.

Trong một datacenter thì hiếm khi đáng: lợi ích hiếm khi bù được complexity. Tools: Tungsten Replicator (MySQL), BDR (PostgreSQL), GoldenGate (Oracle).

Handling Write Conflicts

Nhấn → để chạy từng bước.

SYNC vs ASYNC CONFLICT DETECTION

Single-leader: writer thứ 2 block hoặc abort. Multi-leader: cả hai thành công, conflict phát hiện sau đó — có thể đã quá muộn để hỏi user. Detect đồng bộ thì mất lợi thế multi-leader → dùng single-leader cho rồi.

CONFLICT AVOIDANCE

Đơn giản nhất: mọi write cho một record đi qua cùng một leader — vd. route user về “home” datacenter. Thường được khuyến nghị. Hỏng khi phải đổi leader (DC chết, user chuyển vùng).

Multi-Leader Replication Topologies

Replication topology: các đường giao tiếp mà write lan truyền từ node này sang node khác. Hai leader thì chỉ có một cách; > 2 leader thì nhiều lựa chọn.

(a) Circular

Mặc định của MySQL: nhận từ một node, forward (kèm write của mình) sang node kế.

(b) Star

Một root node forward tới mọi node khác; tổng quát hoá thành tree.

(c) All-to-all

Quorums for reading and writing

w + r > n
  • n replicas; write phải được w node xác nhận; read query ít nhất r node.
  • Tập node đã write và tập node đọc phải overlap → ít nhất 1 node trong r có giá trị mới nhất. Gọi là quorum reads & writes — r, w là số “phiếu” tối thiểu.
  • Phổ biến: n lẻ (3 hoặc 5), w = r = ⌈(n + 1) / 2⌉. Read nhiều write ít → w = n, r = 1: read nhanh nhưng 1 node chết là mọi write fail.
  • w < n → vẫn write khi 1 node down; r < n → vẫn read. n = 3 chịu được 1 node down; n = 5 (w = r = 3) chịu được 2.
  • Request luôn gửi tới cả n replica; w, r chỉ quyết định chờ bao nhiêu response. Không đủ w/r node → error.

Limitations of Quorum Consistency

Quorum không nhất thiết là majority — chỉ cần read set và write set overlap. Đặt w + r ≤ n: dễ đọc stale hơn nhưng latency thấp, availability cao. Dù w + r > n vẫn có edge cases trả về stale value:

  • Sloppy quorum: w writes có thể nằm ở node khác r reads → hết overlap.
  • Hai write concurrent: không rõ cái nào trước; chọn theo timestamp (LWW) → mất write do clock skew.
  • Write concurrent với read: mới reflect ở một số replica → read ra cũ hay mới là không xác định.
  • Write thành công < w replica (vd. disk đầy) → báo fail nhưng không rollback ở replica đã ghi.
  • Node có value mới chết, restore từ replica có value cũ → số replica có value mới tụt dưới w.
  • Kể cả mọi thứ đúng vẫn có thể “unlucky with timing” (Linearizability, Chapter 9).
KHÔNG PHẢI GUARANTEE TUYỆT ĐỐI

Dynamo-style DB tối ưu cho use case chịu được eventual consistency. w, r chỉ chỉnh xác suất đọc stale. Thường không có read-your-writes, monotonic reads, consistent prefix reads.

📊 Monitoring staleness

Leader-based: đo replication lag = vị trí log của leader − vị trí của follower. Leaderless: không có thứ tự apply cố định → khó đo; chỉ có read repair thì value ít đọc có thể cũ tuỳ ý.

Eventual consistency là guarantee cố ý mơ hồ, nhưng để vận hành thì cần quantify “eventual”.

The “happens-before” relationship and concurrency

Operation A happens before B nếu B biết về A, phụ thuộc A, hoặc xây trên A. Hai operation là concurrent nếu không cái nào happens before cái kia (không biết về nhau).

A→B

A happened before B
B ghi đè A

B→A

B happened before A
A ghi đè B

A∥B

A và B concurrent
→ conflict cần resolve

Ví dụ

Figure “overtake”: insert → increment là causally dependent (B xây trên giá trị A insert). Figure concurrent writes: hai client đều không biết nhau → concurrent.

Concurrency, Time, and Relativity: không quan trọng chúng có chồng lấn về thời gian vật lý hay không. Network chậm/gián đoạn → hai operation cách nhau một lúc vẫn concurrent vì không cái nào biết cái kia (liên tưởng tới special relativity: thông tin không đi nhanh hơn ánh sáng).

Version vectors

Nhiều replica cùng nhận write, không leader → một version number là không đủ. Cần version number per replica, per key.

  • Mỗi replica tăng version của chính nó khi xử lý write, và track version đã thấy từ các replica khác.
  • Tập version của mọi replica = version vector. Biến thể hay: dotted version vector (Riak 2.0).
  • Gửi về client khi read, client gửi lại khi write (Riak gọi là causal context) → phân biệt overwrite vs concurrent write.
  • An toàn khi read từ replica này rồi write sang replica khác — có thể sinh siblings, nhưng không mất data nếu merge đúng.

Phục vụ nhiều read hơn một máy.

Single-leader

Mọi write → leader; stream change tới followers. Dễ hiểu, không lo conflict. Read từ follower có thể stale.

Multi-leader

Write tới một trong nhiều leader; leaders gửi change cho nhau.

Leaderless

Write tới nhiều node, read song song nhiều node để phát hiện & sửa stale data.

Multi-leader & leaderless robust hơn với faulty nodes, network interruptions, latency spikes — đổi lại khó suy luận, consistency guarantees rất yếu. Async nhanh khi trơn tru, nhưng promote follower async khi leader chết → mất data đã commit.
