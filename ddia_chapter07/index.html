02

The Slippery Concept of a Transaction

🏛️

1975 · IBM System R

SQL database đầu tiên. Transaction support của MySQL, PostgreSQL, Oracle, SQL Server… giống System R đến kỳ lạ — gần như không đổi suốt 40 năm.

🌪️

Late 2000s · NoSQL

Data model mới, replication & partitioning mặc định. Transactions là “nạn nhân” chính: bị bỏ hẳn, hoặc định nghĩa lại thành guarantee yếu hơn nhiều.

⚖️

Hai luồng hype

“Transactions là kẻ thù của scalability” vs “transaction là bắt buộc cho serious applications với valuable data”. Cả hai đều là pure hyperbole.

Sự thật: như mọi lựa chọn thiết kế kỹ thuật, transactions có advantages và limitations. Để hiểu trade-off, phải xem chính xác chúng đảm bảo điều gì — cả lúc bình thường lẫn trong các tình huống cực đoan (nhưng thực tế).

❓ Có cần transaction không? Không phải app nào cũng cần; đôi khi nới lỏng guarantee để đạt higher performance / availability. Một số safety property đạt được mà không cần transaction.

📍 Chương này áp dụng cho cả single-node lẫn distributed databases; đào sâu concurrency control. Chapter 8 mới bàn riêng về thách thức của distributed systems.

The Meaning of ACID

Thuật ngữ do Theo Härder & Andreas Reuter đặt năm 1983 để mô tả chính xác các fault-tolerance mechanism trong database.

AAtomicity
CConsistency
IIsolation

THỰC TẾ

ACID của database này ≠ ACID của database khác. Riêng isolation đã rất mơ hồ. Ngày nay “ACID compliant” không cho biết chắc bạn nhận được guarantee gì — ACID gần như thành marketing term.

BASE

Hệ thống không đạt ACID đôi khi được gọi là BASE: Basically Available, Soft state, Eventual consistency. Còn mơ hồ hơn ACID — định nghĩa hợp lý duy nhất có lẽ là “not ACID”.

07

Handling errors and aborts

ACID PHILOSOPHY

Nếu sắp vi phạm atomicity, isolation hay durability, database thà bỏ hẳn transaction còn hơn để nó dở dang.

BEST EFFORT

Leaderless replication: “database làm được bao nhiêu thì làm, gặp lỗi cũng không undo” → app tự recover.

ORM như Rails ActiveRecord, Django không retry aborted transaction — exception nổi lên, input của user bị vứt. Đáng tiếc: mục đích của abort là cho phép retry an toàn.

Retry đơn giản & hiệu quả, nhưng không hoàn hảo

✅❓ Commit thành công nhưng ack bị mất

Client tưởng fail → retry → thực hiện 2 lần, trừ khi có deduplication ở application level.

🔥 Lỗi do overload

Retry làm tệ hơn → giới hạn số lần, exponential backoff.

⏳ Chỉ retry transient errors

deadlock, isolation violation, network tạm đứt, failover. Permanent error (constraint violation) thì retry vô ích.

📧 Side effects ngoài database

Gửi email không nên lặp mỗi lần retry. Cần nhiều hệ thống cùng commit/abort → two-phase commit (Ch.9).

💀 Client chết khi đang retry

Data đang định ghi bị mất.

Weak Isolation Levels

Hai transaction không đụng cùng data → chạy song song an toàn. Race condition chỉ xuất hiện khi một transaction đọc data mà transaction khác đang sửa, hoặc cả hai cùng sửa một data.

CONCURRENCY BUGS

Khó tìm bằng testing (chỉ xảy ra khi “xui” về timing), khó reproduce, khó suy luận trong app lớn. Đã gây mất tiền thật, bị financial auditor điều tra, làm hỏng customer data.

“Dùng ACID database nếu xử lý financial data!” — trật trọng tâm: nhiều relational DB “ACID” nổi tiếng vẫn dùng weak isolation mặc định.
Thay vì tin mù quáng vào tool, cần hiểu các loại concurrency problem và cách phòng tránh chúng.

09b

Implementing read committed

Level rất phổ biến — default của Oracle 11g, PostgreSQL, SQL Server 2012, MemSQL và nhiều DB khác.

🔒

Dirty writes → row-level locks

Muốn sửa object (row/document) phải lấy lock và giữ đến khi commit/abort. Transaction khác muốn ghi cùng object phải chờ. DB làm tự động.

🐢

Dirty reads bằng read lock?

Bắt reader lấy lock ngắn hạn… Không ổn: một long-running write làm mọi read-only transaction phải chờ → response time tệ, ảnh hưởng dây chuyền (bad operability).

🗂️

Cách phổ biến: giữ 2 giá trị

Với mỗi object đang được ghi, DB nhớ old committed value và new value. Reader khác nhận old value cho đến khi commit.

Snapshot Isolation

Mỗi transaction đọc từ một consistent snapshot: thấy mọi data đã committed tại thời điểm bắt đầu transaction. Data sau đó có bị sửa, transaction vẫn chỉ thấy data cũ “đóng băng”.

PostgreSQLMySQL / InnoDBOracleSQL Server
BOON

Cho các long-running, read-only queries như backup, analytics: dễ suy luận hơn hẳn khi data không thay đổi dưới chân query.

Key principle: readers never block writers, and writers never block readers.

Hiện thực: MVCC

Write vẫn dùng write lock (chặn dirty write), nhưng read không cần lock. DB giữ nhiều committed versions của một object vì nhiều transaction cần thấy DB ở các thời điểm khác nhau → multi-version concurrency control (MVCC).

Preventing Lost Updates

Lost update xảy ra với chu trình read-modify-write: hai transaction làm đồng thời → write sau clobbers write trước (Figure 7-1).

increment counter / account balancethêm phần tử vào list trong JSON2 người cùng sửa wiki page

① Atomic write operations

Thường là giải pháp tốt nhất nếu diễn đạt được. Concurrency-safe trong hầu hết relational DB:

1UPDATE counters SET value = value + 1 WHERE key = 'foo';

MongoDB: atomic update một phần JSON · Redis: atomic ops trên priority queue… Hiện thực bằng exclusive lock khi đọc (cursor stability) hoặc chạy mọi atomic op trên single thread. ⚠️ ORM dễ vô tình sinh read-modify-write không an toàn.

② Explicit locking · Example 7-1

Multiplayer game: nước đi phải đúng luật — logic không viết được thành query → app tự lock rows:

1BEGIN TRANSACTION;
2SELECT * FROM figures
3 WHERE name = 'robot' AND game_id = 222
4 FOR UPDATE;
5-- Check whether move is valid, then update the position
6-- of the piece that was returned by the previous SELECT.
7UPDATE figures SET position = 'c4' WHERE id = 1234;
8COMMIT;

Chạy được — nhưng dễ quên thêm lock ở đâu đó → race condition.

Lost updates: detect, CAS & replication

③ Automatically detecting

Cho chạy song song; transaction manager phát hiện lost update → abort và bắt retry. Làm hiệu quả cùng snapshot isolation.

PostgreSQL repeatable read ✓Oracle serializable ✓SQL Server snapshot ✓MySQL/InnoDB repeatable read ✗

Ưu điểm lớn: không cần app code làm gì đặc biệt → ít lỗi hơn.

④ Compare-and-set

Ở DB không có transaction: chỉ update nếu giá trị chưa đổi từ lần đọc trước; không khớp → retry.

1-- This may or may not be safe, depending on the database implementation
2UPDATE wiki_pages SET content = 'new content'
3 WHERE id = 1234 AND content = 'old content';

⚠️ Nếu WHERE đọc từ old snapshot thì vẫn có thể lost update. Kiểm tra trước khi tin.

⑤ Conflict resolution & replication

Multi-leader / leaderless: không có “single up-to-date copy” → lock & CAS không áp dụng được.

  • Cho phép tạo nhiều siblings, app/data structure merge sau
  • Commutative atomic ops (increment, add to set) — ý tưởng của Riak 2.0 datatypes
  • Last write wins (LWW) dễ gây lost update — nhưng lại là default ở nhiều replicated DB 😬

Characterizing write skew

Không phải dirty write, không phải lost update (update 2 object khác nhau) — nhưng rõ ràng là race condition: chạy lần lượt thì người thứ hai đã bị chặn.

Write skew = generalization của lost update: hai transaction đọc cùng objects, rồi update một số trong đó (có thể khác nhau). Update cùng object → dirty write / lost update.

Lựa chọn bị thu hẹp

  • ❌ Atomic single-object ops: vô dụng — nhiều object
  • ❌ Auto lost-update detection: PG repeatable read, MySQL, Oracle serializable, SQL Server snapshot đều không phát hiện
  • ⚠️ Multi-object constraint: hiếm DB hỗ trợ (dùng trigger / materialized view)
  • ✅ Serializable isolation, hoặc second-best: SELECT … FOR UPDATE lock các row mà transaction phụ thuộc

More write skew & Phantoms

📅 Meeting room booking

Check không có booking trùng giờ rồi insert → hai người cùng book được.

🎮 Multiplayer game

Lock 1 figure không chặn 2 figure khác di chuyển vào cùng ô.

🪪 Claiming a username

Check tên chưa ai dùng rồi tạo account. Fix đơn giản: unique constraint.

💸 Double-spending

Hai khoản chi insert đồng thời, cộng lại làm balance âm.

Example 7-2 · not safe under snapshot isolation

1BEGIN TRANSACTION;
2-- Check for any existing bookings that overlap with the period of noon-1pm
3SELECT COUNT(*) FROM bookings
4 WHERE room_id = 123 AND end_time > '2015-01-01 12:00' AND start_time < '2015-01-01 13:00';
5-- If the previous query returned zero:
6INSERT INTO bookings
7 (room_id, start_time, end_time, user_id)
8 VALUES (123, '2015-01-01 12:00', '2015-01-01 13:00', 666);
9COMMIT;

Pattern chung của write skew

① SELECT kiểm tra requirement

Tìm các row khớp search condition (≥2 doctors? không có booking trùng?).

② App quyết định

Dựa trên kết quả: đi tiếp, hay báo lỗi và abort.

③ Write (INSERT / UPDATE / DELETE) rồi commit

Write này làm thay đổi precondition của bước ②: chạy lại SELECT sẽ ra kết quả khác.

PHANTOM

Ví dụ doctors: lock được các row ở bước ① bằng FOR UPDATE. Nhưng 4 ví dụ kia kiểm tra sự vắng mặt của row — query trả về 0 row thì không có gì để gắn lock. Một write ở transaction này làm thay đổi kết quả search query của transaction khác = phantom.

Snapshot isolation tránh phantom cho read-only query, nhưng trong read-write transaction, phantom gây ra các ca write skew rất khó.

15b

Materializing conflicts

Phantom không có object để lock? → tạo ra object lock một cách nhân tạo.

  • Tạo bảng room × time slot (vd. mỗi slot 15 phút) cho 6 tháng tới, tạo sẵn mọi row.
  • Transaction book phòng: SELECT … FOR UPDATE các row slot tương ứng, rồi mới check overlap và insert.

Serializability

Một tình cảnh buồn

  • Isolation level khó hiểu, mỗi DB hiện thực một kiểu (“repeatable read” khác nhau rất nhiều).
  • Nhìn application code khó biết có an toàn ở một isolation level hay không.
  • Không có tool tốt để phát hiện race condition; concurrency test thì nondeterministic.
Từ thập niên 1970 tới nay, câu trả lời của giới nghiên cứu vẫn đơn giản: use serializable isolation!

Serializable = level mạnh nhất: dù chạy song song, kết quả như chạy lần lượt từng cái. Transaction đúng khi chạy một mình → vẫn đúng khi chạy đồng thời. DB chặn mọi race condition.

Two-Phase Locking (2PL)

2PL ≠ 2PC

~30 năm là thuật toán serializability duy nhất được dùng rộng rãi. Nhiều transaction được đọc cùng object, nhưng ai muốn ghi thì cần exclusive access:

  • A đã đọc, B muốn ghi → B chờ A commit/abort
  • A đã ghi, B muốn đọc → B chờ (không được đọc version cũ)
Writers chặn writers và readers, ngược lại cũng vậy. Trái với mantra của snapshot isolation: readers never block writers…. Đổi lại: chặn mọi race condition kể cả lost updates và write skew.

Dùng trong: MySQL (InnoDB) & SQL Server serializable, DB2 repeatable read.

  • Overhead lấy/nhả lock, quan trọng hơn: giảm concurrency

Serializable Snapshot Isolation (SSI)

Một bên: serializability nhưng chậm (2PL) hoặc khó scale (serial). Bên kia: weak isolation nhanh nhưng dính race condition. SSI (2008, PhD thesis của Michael Cahill): full serializability với penalty nhỏ so với snapshot isolation. Dùng trong PostgreSQL ≥ 9.1 (serializable) và FoundationDB.

Performance of SSI

  • Granularity tracking: chi tiết → abort chính xác nhưng bookkeeping tốn; thô → nhanh nhưng abort thừa. PostgreSQL dùng lý thuyết để giảm abort không cần thiết.

vs 2PL

Không block chờ lock. Writers không block readers và ngược lại → latency dễ đoán; read-only query chạy trên snapshot không cần lock.

vs serial execution

Không bị giới hạn một CPU core: FoundationDB phân tán conflict detection qua nhiều máy.

Lưu ý

Tỉ lệ abort quyết định performance → read-write transaction cần ngắn. Dù vậy SSI ít nhạy với transaction chậm hơn 2PL hay serial.

Tóm tắt Chapter 7

Transactions là một abstraction layer: app được “giả vờ” rằng một số concurrency problem và hardware/software fault không tồn tại. Một lớp lớn lỗi thu gọn thành transaction abort — app chỉ cần retry.

🧱 Khi nào cần?

Access pattern đơn giản (đọc/ghi một record) có thể sống không cần transaction. Access pattern phức tạp → transaction giảm mạnh số error case phải nghĩ tới; không có nó, denormalized data dễ out of sync.

🧪 Isolation levels

Read committed, snapshot isolation (“repeatable read”), serializable. Weak isolation chặn một số anomaly, phần còn lại developer tự xử lý (vd. explicit locking).
