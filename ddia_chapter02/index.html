01

Data model: mỗi layer ẩn đi complexity của layer bên dưới

1
Application developer

Nhìn thế giới thực (people, organizations, goods, money flows, sensors…) và model thành objects / data structures + API thao tác chúng.

2
General-purpose data model

Để lưu trữ, biểu diễn data structures bằng JSON / XML documents, tables trong relational database, hoặc graph model.

3
Database engineers

Quyết định biểu diễn JSON/XML/relational/graph data thành bytes trong memory, trên disk, qua network — để query, search, xử lý.

4
Hardware engineers

Biểu diễn bytes bằng electrical currents, pulses of light, magnetic fields…

Vì sao data model quan trọng?

Data model ảnh hưởng sâu sắc không chỉ tới cách viết software, mà cả cách ta suy nghĩ về bài toán.

Abstraction giúp phối hợp

Mỗi layer cung cấp một clean data model → các nhóm người khác nhau (database vendor vs application developer) làm việc hiệu quả với nhau.

Mỗi model đều có assumptions

Có usage dễ, có usage không hỗ trợ; có operation nhanh, có operation chậm; có transformation tự nhiên, có cái gượng ép → phải chọn model phù hợp với application.

Nhấn → để chạy từng bước.

Relational Model: thống trị 25–30 năm

Edgar Codd · 1970

Data được tổ chức thành relations (SQL gọi là tables), mỗi relation là một tập không thứ tự các tuples (rows). Lúc đầu chỉ là đề xuất lý thuyết — nhiều người nghi ngờ có implement hiệu quả được không.

03

The Birth of NoSQL

Cái tên “NoSQL” không chỉ một công nghệ cụ thể nào — ban đầu chỉ là một Twitter hashtag cho một meetup năm 2009 về open source, distributed, nonrelational databases.

#NoSQL→Not Only SQL

Về sau được diễn giải lại (retroactively) thành Not Only SQL.

Polyglot persistence: relational databases sẽ tiếp tục được dùng song song với nhiều loại nonrelational datastore — mỗi use case một lựa chọn tốt nhất.

Động lực thúc đẩy NoSQL

📈

Scalability

Cần scale hơn mức relational DB dễ đạt được: dataset rất lớn hoặc write throughput rất cao.

🆓

Open source

Ưa chuộng free & open source software hơn các commercial database product.

🔎

Specialized queries

Những query operation đặc thù mà relational model hỗ trợ không tốt.

🧩

Schema linh hoạt

Khó chịu với tính gò bó của relational schema; muốn data model dynamic & expressive hơn.

04

The Object-Relational Mismatch

Code viết bằng OOP, data nằm trong tables/rows/columns → cần một translation layer vụng về ở giữa. Sự lệch pha này gọi là impedance mismatch (mượn từ điện tử).

ORM frameworks như ActiveRecord, Hibernate giảm boilerplate, nhưng không thể ẩn hoàn toàn khác biệt giữa hai model.

Résumé (LinkedIn profile): one-to-many

① Normalized tables (trước SQL:1999)

positions, education, contact_info ở bảng riêng, có foreign key trỏ về users.

② Structured datatypes / XML / JSON

SQL mới hơn cho lưu multi-valued data trong một row, query & index được (Oracle, DB2, SQL Server, PostgreSQL; JSON: DB2, MySQL, PostgreSQL).

③ Encode JSON/XML vào text column

Application tự diễn giải — thường không query được giá trị bên trong.

Many-to-One: lưu ID hay lưu text?

Vì sao region_id và industry_id là ID, không phải chuỗi "Greater Seattle Area", "Philanthropy"? Đổi tên region thử xem:

Lưu text (duplicate)
user 251 · Greater Seattle Area
user 252 · Greater Seattle Area
user 253 · Greater Seattle Area
user 254 · Greater Seattle Area
Lưu ID (normalized)
user 251 · us:91
user 252 · us:91
user 253 · us:91
user 254 · us:91
regions · us:91 → Greater Seattle Area
Loại bỏ duplication chính là ý tưởng cốt lõi của normalization. Rule of thumb: nếu đang duplicate giá trị có thể lưu ở một chỗ → schema chưa normalized.

Nhấn → để chạy từng bước.

Lợi ích của standardized lists (drop-down / autocompleter)

  • Consistent style & spelling giữa các profile
  • Tránh ambiguity (nhiều thành phố trùng tên)
  • Dễ update — tên chỉ lưu một chỗ (vd. đổi tên thành phố vì sự kiện chính trị)
  • Localization — dịch danh sách chuẩn sang ngôn ngữ của người xem
  • Better search — tìm philanthropists ở bang Washington khớp profile này vì list biết Seattle ∈ Washington

Nhưng: many-to-one không hợp document model

Nhiều người sống ở một region, nhiều người làm một industry. Relational: refer theo ID là bình thường vì join dễ. Document DB: join yếu → phải emulate join trong application code bằng nhiều query.

Are Document Databases Repeating History?

IBM IMS · 1968

Information Management System — database phổ biến nhất cho business data processing thập niên 1970. Ban đầu dùng cho stock-keeping trong chương trình Apollo. Đến nay vẫn chạy trên OS/390 trên IBM mainframes.

Hierarchical model ≈ JSON

Mọi data là tree of records nested within records — rất giống JSON của document DB. Tốt cho one-to-many; nhưng many-to-many khó và không có joins.

Developer phải chọn…

duplicate (denormalize) data, hoặc tự resolve reference từ record này sang record khác bằng tay. Vấn đề của 1960–70s giống hệt vấn đề với document DB ngày nay.

Hai giải pháp nổi bật — “great debate” suốt 1970s

relational model → SQL, chinh phục thế giớinetwork model → dần chìm vào quên lãng

09

The Network Model (CODASYL)

Chuẩn hóa bởi Conference on Data Systems Languages. Là generalization của hierarchical model: một record có thể có nhiều parent → model được many-to-one & many-to-many.

  • Links giữa records không phải foreign keys mà giống pointers (dù lưu trên disk)
  • Cách duy nhất truy cập record: đi theo đường từ root record dọc chuỗi links — gọi là access path
  • Query = di chuyển một cursor qua database, iterate lists, follow access paths
Ngay cả thành viên CODASYL committee cũng thừa nhận: như đang “navigating around an n-dimensional data space”.
Vấn đề

Tối ưu được phần cứng 1970s (tape drives, seek cực chậm), nhưng code query/update phức tạp, kém linh hoạt. Không có path tới data cần → đổi access path → viết lại hàng loạt handwritten query code.

Nhấn → để chạy từng bước.

10

The Relational Model: data bày ra công khai

Một relation (table) chỉ đơn giản là tập các tuples (rows). Không có nested structure mê cung, không có access path phức tạp.

  • Đọc bất kỳ / tất cả rows, lọc theo điều kiện tùy ý
  • Đọc một row cụ thể bằng cách chọn vài cột làm key
  • Insert row mới vào bất kỳ table nào, không lo foreign key tới/từ bảng khác

Query optimizer

Tự quyết định thực thi phần nào trước, dùng index nào — đó thực chất là “access path”, nhưng được chọn tự động, không phải bởi developer.

Key insight: chỉ cần build query optimizer một lần, mọi application dùng database đều hưởng lợi. General-purpose solution thắng trong dài hạn.

Ghi chú: join trên foreign key diễn ra lúc query time; trong CODASYL, join thực chất xảy ra lúc insert time.

1SELECT * FROM users WHERE region_id = 'us:91';

Relational vs Document Databases Today

Document DB ↔ hierarchical model

Giống hierarchical ở một điểm: nested records (one-to-many như positions, education, contact_info) nằm trong parent record thay vì bảng riêng.

Many-to-one & many-to-many: không khác bản chất

Cả hai đều refer bằng unique identifier — foreign key (relational) / document reference (document), resolve lúc đọc bằng join hoặc follow-up query. Document DB không đi theo con đường CODASYL.

Model nào cho application code đơn giản hơn?

Data dạng document → dùng document model

Tree of one-to-many, thường load cả tree một lần. Kỹ thuật shredding của relational (xé document thành nhiều bảng) → schema cồng kềnh, code phức tạp không cần thiết.

Giới hạn của document model

Không refer trực tiếp tới nested item được, phải nói kiểu “item thứ 2 trong list positions của user 251” (giống access path). Không sao nếu document không nest quá sâu.

Many-to-many

Denormalize → app phải giữ data consistent. Emulate join bằng nhiều request → complexity dồn vào app, chậm hơn join trong database. (Analytics ghi events có thể không cần many-to-many.)

Phụ thuộc vào loại relationship giữa các data item

📄 document: natural 🗃️ relational: acceptable 🕸️ graph: most natural
tree · self-contained→ mức độ interconnected →anything ↔ everything
Với data highly interconnected: document model awkward, relational acceptable, graph model natural nhất. Không thể nói chung chung model nào đơn giản hơn.

13

Schema flexibility: schema-on-read vs schema-on-write

Document DB thường bị gọi là schemaless — dễ gây hiểu lầm: code đọc data vẫn giả định một cấu trúc nào đó → có implicit schema, chỉ là database không enforce.

📖 schema-on-read

Cấu trúc implicit, chỉ được diễn giải khi đọc. ≈ dynamic (runtime) type checking.

✍️ schema-on-write

Schema explicit, database đảm bảo mọi data ghi vào tuân thủ. ≈ static (compile-time) type checking.

Schema change có chậm không?

ALTER TABLE chạy trong vài ms ở hầu hết RDBMS. Ngoại lệ: MySQL copy cả table → có thể downtime hàng phút/giờ (có tools để né). UPDATE bảng lớn thì chậm ở mọi DB → có thể để NULL rồi fill lúc đọc, như document DB.

Schema-on-read có lợi khi data heterogeneous: quá nhiều loại object để mỗi loại một table, hoặc cấu trúc do external system quyết định và có thể đổi bất kỳ lúc nào. Còn khi mọi record cùng cấu trúc → schema là cơ chế hữu ích để document & enforce.

Ví dụ: tách full name thành first_name + last_name

Document DB · xử lý document cũ trong app code
Relational · migration

Data locality for queries

Document thường lưu thành một chuỗi liên tục: JSON, XML hoặc binary variant (vd. BSON của MongoDB). Cần cả document (vd. render web page) → lợi thế storage locality.

Relational (Figure 2-1): nhiều index lookups → nhiều disk seeks

Document: một lần đọc tuần tự

Nhấn → để chạy từng bước.

Nhưng locality chỉ có lợi khi…

cần phần lớn document cùng lúc. DB thường load cả document dù chỉ cần một phần nhỏ. Update → thường phải rewrite toàn bộ document (trừ khi không đổi encoded size). → Nên giữ document nhỏ, tránh write làm document to ra.

Locality không chỉ của document model

  • Google Spanner: schema khai báo rows của table được interleaved (nested) trong parent table
  • Oracle: multi-table index cluster tables
  • Bigtable (Cassandra, HBase): khái niệm column-family để quản lý locality
15

Convergence of document & relational databases

🗃️ Relational → document

  • Hỗ trợ XML từ giữa 2000s (trừ MySQL): sửa cục bộ, index & query bên trong XML document
  • JSON: PostgreSQL 9.3, MySQL 5.7, IBM DB2 10.5 — JSON phổ biến cho web APIs nên DB khác sẽ theo
⇄

📄 Document → relational

  • RethinkDB hỗ trợ relational-like joins trong query language
  • Vài MongoDB drivers tự resolve database references (client-side join — chậm hơn vì thêm network round-trips)
Hai model bổ sung cho nhau. DB xử lý được document-like data và chạy relational queries → app dùng tổ hợp feature phù hợp nhất. Hybrid là hướng đi tốt.
Footnote: mô tả gốc của Codd đã cho phép thứ gần giống JSON trong relational schema — nonsimple domains: giá trị trong row có thể là một nested relation, sớm hơn JSON/XML support của SQL 30 năm.

MapReduce Querying

MapReduce: programming model xử lý lượng data lớn theo bulk trên nhiều máy, phổ biến bởi Google. Một dạng giới hạn có trong MongoDB, CouchDB để chạy read-only queries trên nhiều documents (chi tiết ở Chapter 10).

Nằm ở giữa

Không declarative hoàn toàn, cũng không imperative hoàn toàn: logic viết bằng snippets of code, được framework gọi lặp lại. Dựa trên map (aka collect) và reduce (aka fold, inject) của functional programming.

map & reduce phải là pure functions

Chỉ dùng input được truyền vào, không chạy thêm database query, không side effects → DB chạy chúng ở đâu cũng được, thứ tự nào cũng được, rerun khi failure. Vẫn mạnh: parse string, gọi library, tính toán…

MapReduce khá low-level

SQL có thể implement thành pipeline các MapReduce operations, nhưng cũng có nhiều distributed SQL không dùng MapReduce. SQL không bị giới hạn ở một máy; MapReduce không độc quyền distributed query execution.

Aggregation pipeline: “reinventing SQL”

Usability problem của MapReduce

Phải viết hai JavaScript functions phối hợp cẩn thận — thường khó hơn viết một query. Declarative language cũng cho optimizer nhiều cơ hội hơn.

Property Graphs

Vertex

  • unique identifier
  • set of outgoing edges
  • set of incoming edges
  • properties (key-value)

Edge

  • unique identifier
  • tail vertex (bắt đầu)
  • head vertex (kết thúc)
  • label mô tả relationship
  • properties (key-value)

Đặc điểm quan trọng

① Vertex bất kỳ có thể nối với vertex bất kỳ — không có schema giới hạn loại liên kết.

② Từ một vertex, tìm nhanh cả incoming & outgoing edges → traverse cả xuôi lẫn ngược (vì thế có index trên cả hai cột).

③ Dùng labels khác nhau → nhiều loại thông tin trong một graph mà data model vẫn sạch.

The Semantic Web & RDF

Semantic web: ý tưởng đơn giản, hợp lý

Website đã publish text/ảnh cho người đọc — sao không publish thêm machine-readable data cho máy đọc? Resource Description Framework (RDF) giúp các site publish data theo format thống nhất → kết hợp thành một web of data, kiểu “database of everything” cỡ internet.

Thực tế

Overhyped đầu 2000s, chưa thành hiện thực; quá nhiều acronyms, standards phức tạp, và hubris. Nhưng triples vẫn là internal data model tốt cho app. Triple-store độc lập với semantic web — vd. Datomic (thực ra dùng 5-tuples, thêm metadata cho versioning).

URIs làm namespace

Predicate có thể là <http://my-company.com/namespace#within> thay vì WITHIN → ghép data với người khác không conflict. URL không cần resolve; sách dùng urn:example:within, khai báo prefix một lần ở đầu file.

The SPARQL Query Language

Query language cho triple-stores dùng RDF data model. Viết tắt của SPARQL Protocol and RDF Query Language, đọc là “sparkle”. Ra đời trước Cypher — Cypher mượn pattern matching từ SPARQL.

Example 2-9 · cùng query: ai chuyển từ US sang Europe

Còn ngắn gọn hơn Cypher. Biến bắt đầu bằng ?.

Cypher ↔ SPARQL

Traversal
C(person) -[:BORN_IN]-> () -[:WITHIN*0..]-> (location)
S?person :bornIn / :within* ?location.
Property match
C(usa {name:'United States'})
S?usa :name "United States".
RDF không phân biệt properties và edges — chỉ dùng predicates cho cả hai → cùng một syntax để match. SPARQL là công cụ mạnh cho app dùng nội bộ, dù semantic web có thành hay không.

The Foundation: Datalog

Cũ hơn SPARQL/Cypher nhiều, được giới học thuật nghiên cứu kỹ thập niên 1980 — nền tảng cho các query language sau này. Dùng trong Datomic, Cascalog (Hadoop). Datalog là subset của Prolog.

Triple viết thành predicate(subject, object):

Facts · Example 2-10

name(namerica, 'North America').
within(usa, namerica).
within(idaho, usa).
name(lucy, 'Lucy').
born_in(lucy, idaho).

Derived (Figure 2-6)

within_recursive(namerica, 'North America').
within_recursive(usa, 'North America').
within_recursive(idaho, 'North America').

Rules · Example 2-11

within_recursive(Location, Name) :- name(Location, Name). /* Rule 1 */
within_recursive(Location, Name) :- within(Location, Via), /* Rule 2 */ within_recursive(Via, Name).
migrated(Name, BornIn, LivingIn) :- name(Person, Name), /* Rule 3 */ born_in(Person, BornLoc), within_recursive(BornLoc, BornIn), lives_in(Person, LivingLoc), within_recursive(LivingLoc, LivingIn).
?- migrated(Who, 'United States', 'Europe'). /* Who = ? */

Nhấn → để chạy từng bước.

Rule định nghĩa predicate mới, derive từ data hoặc rule khác — như function gọi function, kể cả đệ quy. Biến viết hoa chữ đầu.

Cách nghĩ khác, nhưng mạnh: rules kết hợp & tái sử dụng giữa các query. Kém tiện cho query one-off, nhưng xử lý tốt data phức tạp.

Tóm tắt Chapter 2

Lịch sử: data ban đầu là một cây lớn (hierarchical model) — không hợp many-to-many → relational model ra đời. Gần đây một số app không hợp relational → NoSQL rẽ hai hướng:

📄 Document

Data là các self-contained documents, quan hệ giữa document hiếm khi có.

🗃️ Relational

Joins, many-to-one & many-to-many tốt. Vẫn dùng rộng rãi, đang hội tụ với document (JSON/XML).

🕸️ Graph

Hướng ngược lại: anything is potentially related to everything.

Một model emulate được model khác nhưng thường awkward → mỗi mục đích một hệ thống, không có one-size-fits-all. Document & graph thường không enforce schema — câu hỏi là schema explicit (on write) hay implicit (on read).

Query languages: SQL, MapReduce, aggregation pipeline, Cypher, SPARQL, Datalog (+ CSS, XSL/XPath). Còn nhiều model khác: genome (GenBank), LHC hàng trăm petabytes, full-text search.
