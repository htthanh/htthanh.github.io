01

Batch giả định input bounded — thực tế data là unbounded

BATCH (Chapter 10)

Input có kích thước known & finite → job biết khi nào đọc xong. Ví dụ sort trong MapReduce phải đọc hết input mới bắt đầu output được.

THỰC TẾ

User tạo data hôm qua, hôm nay, ngày mai… dataset không bao giờ “complete”. Batch phải chia data thành chunk thời gian cố định: mỗi ngày, mỗi giờ.

STREAM PROCESSING

Bỏ hẳn fixed time slices: xử lý từng event ngay khi nó xảy ra. “Stream” = data được tạo ra dần dần theo thời gian (stdin/stdout, TCP, lazy lists, audio/video…).

03

Messaging Systems: publish/subscribe & 2 câu hỏi

Unix pipe / TCP nối đúng 1 sender ↔ 1 recipient. Messaging system cho phép nhiều producer gửi vào cùng topic và nhiều consumer nhận từ topic đó.

❶ Producer gửi nhanh hơn consumer xử lý thì sao?

🗑️ Drop messages

P→mmm→C

Bỏ bớt message. Chấp nhận được với metrics/sensor gửi định kỳ, nhưng nguy hiểm khi counting events.

📦 Buffer in a queue

P→→C

Queue lớn dần: hết memory thì crash hay ghi xuống disk? Disk access ảnh hưởng performance ra sao?

✋ Backpressure

P ⛔ blocked→→C

Còn gọi là flow control: chặn producer đến khi buffer có chỗ. Unix pipes và TCP dùng cách này.

❷ Node crash / offline — có mất message không?

Durability cần ghi xuống disk và/hoặc replication — có chi phí. Nếu chấp nhận đôi khi mất message → throughput cao hơn, latency thấp hơn trên cùng hardware.

Batch (Chapter 10) có reliability guarantee mạnh: task fail được retry, partial output bị discard → output như thể không có failure. Cuối chương sẽ xem stream đạt được điều tương tự thế nào.

Direct messaging vs Message brokers

DIRECT · không qua node trung gian
  • UDP multicast: stock market feeds, low latency; protocol tầng app tự retransmit packet bị mất.
  • ZeroMQ, nanomsg: brokerless pub/sub trên TCP hoặc IP multicast.
  • StatsD, Brubeck: thu metrics qua UDP không reliable → counter chỉ xấp xỉ.
  • Webhooks: đăng ký callback URL, service kia gọi HTTP/RPC khi có event.
Hạn chế: app phải biết có thể mất message; giả định producer & consumer luôn online. Consumer offline → bỏ lỡ message; producer crash → mất buffer retry.

07

Partitioned Logs: durable storage + low-latency notification

TRANSIENT MESSAGING MINDSET
  • Gửi packet/request: không để lại dấu vết lâu dài.
  • AMQP/JMS: nhận message là destructive — ack → bị xoá → chạy lại consumer không ra cùng kết quả.
  • Consumer mới chỉ thấy message gửi sau khi đăng ký; message cũ đã mất.
vs
DATABASE / FILESYSTEM MINDSET
  • Mọi thứ được ghi lại vĩnh viễn đến khi bị xoá tường minh.
  • Batch job chạy lặp lại thoải mái, input read-only không bị hỏng.
  • Client mới có thể đọc data ghi từ rất lâu trước.
Tại sao không lai cả hai? → log-based message brokers.

📜 Log = append-only sequence of records on disk

Đã gặp ở log-structured storage & write-ahead log (Ch.3), replication (Ch.5). Producer append vào cuối log; consumer đọc tuần tự; tới cuối log thì chờ notification — giống tail -f.

🧱 Partitioned để scale

Log được chia partitions (Ch.6) trên nhiều máy. Topic = nhóm partitions cùng loại message. Ví dụ: Apache Kafka, Amazon Kinesis Streams, Twitter DistributedLog — hàng triệu msg/s, fault tolerance nhờ replication.

Rất giống single-leader replication: broker như leader, consumer như follower. Consumer chết → node khác nhận partition, bắt đầu từ offset đã ghi cuối cùng → có thể xử lý lại vài message.

Throughput cao, mỗi message xử lý nhanh, và ordering quan trọng.

VẤN ĐỀ 1 · RACE CONDITION

Hai client ghi đồng thời, thứ tự đến hai hệ thống khác nhau → hai hệ thống vĩnh viễn lệch nhau, không ai báo lỗi. Cần cơ chế concurrency detection (version vectors…).

Một write thành công, write kia fail → inconsistent. Đảm bảo “cả hai hoặc không” cần atomic commit — đắt (2PC).

State thay đổi nào cũng là kết quả của các events đã làm nó thay đổi: ghế còn trống = kết quả các lần đặt chỗ; số dư = các khoản credit/debit. Mutable state và append-only log of immutable events là hai mặt của một đồng xu.

“Transaction logs record all the changes made to the database… The truth is the log. The database is a cache of a subset of the log. That cached subset happens to be the latest value of each record and index value from the log.” — Pat Helland
Coi event log là system of record, mọi mutable state là derived → dễ suy luận về dataflow. Log compaction là cầu nối giữa log và database state.
13b

Advantages & limitations of immutable events

📒

Ledger

Kế toán dùng immutability hàng thế kỷ: append-only ledger. Ghi sai? Không xoá — thêm compensating transaction. Dễ audit, dễ recover khi code có bug.

🛒

Thêm thông tin

User thêm món vào cart rồi bỏ ra: state hiện tại không còn dấu vết, nhưng event log giữ lại — hữu ích cho analytics (khách đã cân nhắc món đó).

🪟

Nhiều views · CQRS

Từ cùng một event log derive nhiều read-optimized views. Tách nơi data được ghi khỏi cách nó được đọc = Command Query Responsibility Segregation. Tranh luận normalization vs denormalization bớt quan trọng.

🔒

Concurrency control

Views cập nhật asynchronously → user có thể không đọc thấy write của mình. Nhưng một user action = một event, append atomic → giảm nhu cầu multi-object transactions.

LIMITATIONS

Workload nhiều update/delete trên dataset nhỏ → immutable history phình to, fragmentation, compaction & GC phải tốt. Lý do pháp lý/privacy (vd. user xoá account) → phải xoá thật data.

REWRITE HISTORY

Datomic: excision. Fossil VCS: shunning. Xoá thật rất khó vì có nhiều bản copy (storage engine, filesystem, SSD, backups) — thường chỉ là “làm cho khó truy xuất hơn”.

Uses of Stream Processing

🕵️

Complex event processing (CEP)

Tìm patterns của events (như regex trên chuỗi events), khai báo bằng query language (SQL-like). Esper, IBM InfoSphere Streams, Apama, TIBCO StreamBase, SQLstream.

DB: data lâu dài, query thoáng qua
CEP: query lâu dài, data chảy qua
📊

Stream analytics

Aggregation & metrics: rate của event, rolling average, so sánh với cùng kỳ. Tính trên window. Hay dùng probabilistic algorithms: Bloom filters, HyperLogLog, percentile estimation. Apache Storm, Spark Streaming, Flink, Concord, Samza, Kafka Streams; Google Cloud Dataflow, Azure Stream Analytics.

🪞

Maintaining materialized views

Giữ derived data (cache, search index, data warehouse) luôn cập nhật — event sourcing chính là view được maintain bởi stream processor. Cần tất cả events từ đầu (trừ khi compaction), không chỉ một window. Samza, Kafka Streams hỗ trợ.

🔎

Search on streams

Lưu search queries trước, mỗi document đi qua sẽ được khớp với các query (vd. media monitoring, cảnh báo bất động sản mới). Elasticsearch percolator. Có thể index cả queries.

✉️

Message passing & RPC

Actor frameworks chủ yếu để quản lý concurrency & phân tán module giao tiếp, không phải data management; giao tiếp thường ephemeral, one-to-one. Nhưng có điểm giao: vd. Apache Storm có distributed RPC.

Điểm chung: stream processor là long-running, chạy mãi theo events đến — khác query một lần rồi xong.

Reasoning About Time: event time vs processing time

Batch dùng timestamp trong event (deterministic khi chạy lại). Nhiều stream framework lại dùng local system clock của máy xử lý (processing time) — chỉ đúng khi delay giữa lúc event xảy ra và lúc được xử lý không đáng kể. Delay có thể lớn: queueing, network faults, broker contention, consumer restart, replay…

📉 Nhầm lẫn hai loại time → bad data

Đo requests/second. Stream processor bị redeploy, tắt 1 phút rồi xử lý backlog…

15b

Knowing when you're ready · Whose clock are you using?

⏳ Straggler events

Đang đếm window 10:37 theo event time. Khi nào thì chắc chắn đã nhận hết events của window đó? Không bao giờ chắc — có event bị delay ở node khác, đến muộn sau khi đã declare window complete.

Option 1 · Ignore

Bỏ qua straggler (thường chỉ là tỉ lệ nhỏ); track số event bị drop làm metric, alert nếu tăng nhiều.

Option 2 · Publish a correction

Phát lại giá trị đã cập nhật cho window kèm stragglers; có thể phải retract output trước đó.

Producer có thể gửi message đặc biệt “từ giờ không còn message nào có timestamp < t” — nhưng nhiều producer, mỗi cái một threshold riêng → phức tạp.

📱 Device clock không đáng tin

Mobile app có thể dùng offline, buffer events hàng giờ/ngày rồi mới gửi. Device clock có thể sai (cố tình hoặc vô tình). Server clock đúng hơn nhưng ít ý nghĩa với hành động của user.

Log ba timestamps:

t₁ · event occurred

theo device clock

t₂ · event sent to server

theo device clock

t₃ · event received by server

theo server clock

offset ≈ t₃ − t₂  ⇒  true time ≈ t₁ + (t₃ − t₂)

Giả định network delay nhỏ so với độ chính xác cần thiết, và offset của device clock không đổi giữa t₁ và t₂.

16

Types of windows

Tumbling

Độ dài cố định, mỗi event thuộc đúng một window. Cài đặt: làm tròn timestamp xuống phút gần nhất.

Hopping

Độ dài cố định nhưng overlap để smoothing. Tính tumbling 1 phút rồi aggregate nhiều window liền kề.

Sliding

Gồm mọi event nằm trong một khoảng của nhau; không có biên cố định. Giữ buffer sort theo time, bỏ event hết hạn.

Session

Không có duration cố định: gom events của cùng user gần nhau, kết thúc khi user inactive (vd. 30 phút). Dùng cho website analytics.

17b

Stream Joins ②: table-table join

Ví dụ Twitter home timeline cache (Chapter 1): thay vì query khi đọc, giữ cache theo user, cập nhật bằng stream:

✍️ tweet

user gửi tweet mới → thêm vào timeline của mọi follower.

🗑️ delete tweet

xoá khỏi timeline của mọi follower.

➕ follow

u₁ follow u₂ → các tweet gần đây của u₂ thêm vào timeline u₁.

➖ unfollow

tweet của u₂ bị gỡ khỏi timeline u₁.

Stream processor cần giữ DB gồm tập followers của mỗi user — join hai stream (tweets & follows) = maintain materialized view của query:

1SELECT follows.follower_id AS timeline_id,
2 array_agg(tweets.* ORDER BY tweets.timestamp DESC)
3FROM tweets
4JOIN follows
5 ON follows.followee_id = tweets.sender_id
6GROUP BY follows.follower_id

Mọi thay đổi ở một bên được join với state mới nhất của bên kia → output là stream các thay đổi của view (giống product rule: (u·v)′ = u′v + uv′).

TIME-DEPENDENCE OF JOINS

Cả ba loại join đều cần giữ state; nếu state thay đổi theo thời gian, join với phiên bản nào? Vd. bán hàng cần tax rate tại thời điểm bán, không phải hiện tại. Thứ tự giữa các stream không xác định → join nondeterministic.

Data warehouse gọi đây là slowly changing dimension (SCD): gắn version ID cho mỗi phiên bản record (mỗi lần tax rate đổi → ID mới), invoice ghi ID đó → join deterministic, đổi lại không dùng được log compaction.

Fault Tolerance: exactly-once (effectively-once) semantics

Batch: task fail → restart, discard partial output → output như thể mỗi record được xử lý đúng một lần. Stream vô hạn → không thể đợi task xong mới công bố output. Mục tiêu: kết quả như thể không có fault — dù thực tế record có thể được xử lý lại.

📦 Microbatching · Spark Streaming

Chia stream thành block nhỏ (~1 giây) và xử lý như mini batch. Batch nhỏ → overhead scheduling; batch lớn → delay. Ngầm tạo một tumbling window bằng batch size (theo processing time).

🚩 Checkpointing · Apache Flink

Định kỳ tạo rolling checkpoints của state, trigger bởi barriers trong message stream — như ranh giới microbatch nhưng không ép window size.

Trong phạm vi stream framework thì đủ exactly-once. Nhưng output đã rời khỏi framework (ghi DB, gửi email…) thì không thu hồi được → restart sẽ gây side effect hai lần.

Atomic commit · idempotence · rebuilding state

⚛️

Atomic commit revisited

Mọi output & side effect (ghi downstream, message tới broker, ack/offset input) xảy ra khi và chỉ khi xử lý thành công. Không phải XA heterogeneous: giữ transaction nội bộ framework, tận dụng gom nhiều message vào một transaction. Google Cloud Dataflow, VoltDB, Apache Kafka.

🔁

Idempotence

Làm nhiều lần = làm một lần.

SET x = 5 ✓
counter += 1 ✗

Biến write không-idempotent thành idempotent: lưu kèm Kafka offset của message đã ghi → thấy offset đã áp dụng thì bỏ qua. Cần replay đúng thứ tự, processing deterministic, và fencing khi failover (chặn node bị coi là đã chết).

🧱

Rebuilding state after failure

Window aggregations, local table cho join… cần state phục hồi được.

  • Remote datastore + replicate (chậm nếu query mỗi message)
  • Local state + periodic snapshot (Flink)
  • Gửi thay đổi state lên changelog topic có log compaction (Samza, Kafka Streams)
  • Xử lý dư thừa trên nhiều node (VoltDB)
  • Hoặc rebuild từ input stream (window ngắn)
Chọn cách nào tuỳ performance của infrastructure: đôi khi network nhanh hơn disk, đôi khi ngược lại — không có lựa chọn lý tưởng chung.
20

Summary

📨 AMQP/JMS-style message broker

Broker gán từng message cho consumer, consumer ack từng message, ack xong thì xoá. Hợp với asynchronous RPC, task queue: thứ tự không quan trọng, không cần đọc lại message cũ.

📜 Log-based message broker

Broker gán cả partition cho một consumer node, luôn deliver theo cùng thứ tự. Parallelism qua partitioning; consumer track offset. Message giữ trên disk → replay được. Hợp cho derived state & output streams.

🔄 Databases as streams

CDC (ngầm) hoặc event sourcing (tường minh). Log compaction giữ full copy của DB.

🎯 Uses

CEP, stream analytics (windowed aggregation), maintaining materialized views, search on streams.

⏱️ Time

Event time vs processing time; straggler events; tumbling · hopping · sliding · session windows.

🛡️ Fault tolerance

Exactly-once qua microbatching, checkpointing, transactions, hoặc idempotent writes.
