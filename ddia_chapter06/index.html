01

Partitioning là gì?

Chapter 5 nói về replication (nhiều bản copy của cùng data). Với dataset rất lớn hoặc query throughput rất cao, như vậy chưa đủ → cần chia nhỏ data thành partitions.

  • Mỗi record / row / document thuộc về đúng một partition.
  • Mỗi partition là một small database của riêng nó (có thể hỗ trợ operation chạm nhiều partition).
  • Lý do chính: scalability. Các partitions đặt trên nhiều node trong cluster shared-nothing → data trải ra nhiều disk, query load trải ra nhiều processor.
  • Query trên một partition: mỗi node tự chạy độc lập → thêm node = tăng throughput. Query lớn, phức tạp có thể parallelize trên nhiều node (khó hơn nhiều).
Pioneered từ thập niên 1980 bởi Teradata, Tandem NonStop SQL; gần đây được NoSQL databases & Hadoop-based data warehouses “rediscover”. Áp dụng cho cả transactional lẫn analytics workloads.

03

Partitioning of Key-Value Data

Câu hỏi: record nào lưu ở node nào? Mục tiêu: chia data và query load đều cho các node.

  • Chia công bằng → về lý thuyết 10 nodes xử lý được 10× data và 10× read/write throughput.
  • Chia không công bằng = skewed. Partition có load cao bất thường = hot spot. Cực đoan: 9/10 nodes idle, bottleneck là 1 node bận.
  • Gán record cho node ngẫu nhiên? Data đều, nhưng khi đọc một item thì không biết nó ở đâu → phải query tất cả nodes song song.
  • Làm tốt hơn: giả sử data model key-value đơn giản, luôn truy cập record theo primary key — như tra bách khoa toàn thư theo tiêu đề.

06

Partitioning by Hash of Key

Vì rủi ro skew & hot spots, nhiều distributed datastores dùng hash function để quyết định partition của một key.

  • Hash tốt biến data skewed thành uniformly distributed: string 32-bit hash → số “ngẫu nhiên” trong 0 … 232−1, dù input rất giống nhau.
  • Không cần cryptographically strong: Cassandra & MongoDB dùng MD5, Voldemort dùng Fowler–Noll–Vo.
  • Cẩn thận hash built-in: Java Object.hashCode(), Ruby Object#hash — cùng key có thể ra hash khác nhau ở các process khác nhau.
  • Gán mỗi partition một range of hashes (không phải range of keys). Boundaries có thể chia đều, hoặc chọn pseudorandomly.

07

Cái giá của hashing & compound primary key

⚠️ “Consistent Hashing”

Theo Karger et al.: cách phân bố load trên hệ thống cache cỡ internet (như CDN), dùng randomly chosen partition boundaries để khỏi cần central control hay distributed consensus.

“Consistent” ở đây không liên quan replica consistency hay ACID consistency — nó mô tả một cách rebalancing. Không hiệu quả lắm cho databases, docs hay dùng sai.

Gợi ý của tác giả: tránh thuật ngữ này, gọi là hash partitioning.
MẤT RANGE QUERIES

Keys từng kề nhau giờ bị rải khắp partitions → sort order mất.

  • MongoDB (hash-based sharding): range query gửi tới tất cả partitions.
  • Riak, Couchbase, Voldemort: không hỗ trợ range query trên primary key.
CASSANDRA · COMPROMISE

Compound primary key: chỉ phần đầu được hash để chọn partition; các column còn lại là concatenated index để sort trong SSTables.

1CREATE TABLE updates (
2 user_id bigint,
3 update_timestamp timestamp,
4 body text,
5 PRIMARY KEY ((user_id),
6 update_timestamp));

user_id → hash → partition · update_timestamp → sorted trong partition.

08

Skewed Workloads & Relieving Hot Spots

Hashing giảm hot spots nhưng không loại bỏ hoàn toàn: nếu mọi read/write đều vào cùng một key, chúng vẫn tới cùng một partition.

🌟 Celebrity problem

Celebrity có hàng triệu followers làm gì đó → “storm of activity”: rất nhiều write vào cùng key (user ID của celebrity, hoặc ID của action được comment). Hash của hai ID giống nhau vẫn giống nhau.

Giải pháp ở application

Đa số data systems chưa tự bù được skew này → application phải tự làm: thêm random number 2 chữ số vào đầu/cuối key → chia writes cho 100 keys khác nhau, nằm ở các partitions khác nhau.

TRADE-OFF

Read phải đọc cả 100 keys rồi combine. Cần bookkeeping: chỉ split các hot keys (số ít), và phải theo dõi key nào đang bị split.

09

Partitioning and Secondary Indexes

Các scheme trên dựa vào key-value model: biết primary key → biết partition → route request.

Với secondary index, mọi thứ phức tạp hơn: nó thường không xác định record duy nhất mà là cách tìm các occurrences của một value:

all actions by user 123articles containing “hogwash”cars whose color is red
  • “Bread and butter” của relational databases, phổ biến cả ở document databases.
  • Nhiều key-value stores (HBase, Voldemort) tránh vì phức tạp; một số (Riak) bắt đầu thêm vào vì quá hữu ích.
  • Là raison d’être của search servers như Solr, Elasticsearch.
VẤN ĐỀ

Secondary indexes không map gọn gàng vào partitions.

📄 Document-based

Mỗi partition giữ index cho documents của nó → local index.

🔤 Term-based

Một index chung, được partition theo term → global index.

Ví dụ xuyên suốt: website bán xe cũ, partition theo document ID (0–499 ở partition 0, 500–999 ở partition 1), cần filter theo color và make.

Term-partitioned

Index chung không thể đặt trên một node (sẽ thành bottleneck) → index cũng phải partition, nhưng khác primary key. Term (vd. color:red) quyết định partition của index — tên gọi đến từ full-text indexes.

Partition theo term → range scans (vd. asking price); theo hash of term → load đều hơn.

WRITE: CHẬM & PHỨC TẠP

Index luôn up-to-date cần distributed transaction qua mọi partition liên quan — không phải DB nào cũng hỗ trợ. Thực tế update global index thường asynchronous.

DynamoDB: global secondary indexes cập nhật trong “a fraction of a second” bình thường, có thể lâu hơn khi infrastructure gặp fault. Cũng dùng ở Riak search, Oracle data warehouse.

Rebalancing Partitions

Theo thời gian, mọi thứ thay đổi → data & requests phải chuyển từ node này sang node khác. Quá trình di chuyển load trong cluster gọi là rebalancing.

📈

Query throughput tăng

Cần thêm CPUs để xử lý load.

💾

Dataset size tăng

Cần thêm disks và RAM để lưu trữ.

💥

Machine fails

Máy khác phải take over trách nhiệm của máy hỏng.

Minimum requirements cho rebalancing

⚖️ Fair share

Sau rebalancing, load (storage, reads, writes) chia công bằng giữa các node.

🟢 Online

Trong lúc rebalancing, database vẫn nhận reads & writes.

🚚 Move tối thiểu

Không di chuyển data nhiều hơn cần thiết → nhanh, ít network & disk I/O.

How not to do it: hash mod N

Sao không chia hash thành ranges mà dùng luôn hash(key) % N? Với 10 nodes, hash % 10 → 0…9, trông rất tiện.

hash(key) = 123456
N = 10 → node 6 N = 11 → node 3 N = 12 → node 0

Ưu điểm

Có thể bù cho mismatched hardware: node mạnh nhận nhiều partitions hơn. Dùng ở Riak, Elasticsearch, Couchbase, Voldemort.

Chọn số partitions

Thường cố định từ lúc setup (đơn giản hơn split/merge). Số partitions = số node tối đa → phải chọn đủ lớn cho tương lai, nhưng mỗi partition có management overhead.

KHÓ KHI DATASET BIẾN ĐỘNG

Kích thước partition ∝ tổng data. Quá lớn → rebalancing & recovery đắt; quá nhỏ → overhead. Khó đạt mức “just right”.

ƯU ĐIỂM

Số partitions thích nghi với tổng data volume: ít data → ít partitions, overhead nhỏ; nhiều data → mỗi partition bị giới hạn ở một max size.

CAVEAT

Lúc đầu chỉ 1 partition → mọi write vào 1 node. Giải pháp: pre-splitting (HBase, MongoDB) — cấu hình sẵn initial partitions; với key range thì phải biết trước key distribution.

Không chỉ cho key range: MongoDB (từ 2.4) hỗ trợ cả key-range lẫn hash partitioning, và split dynamically trong cả hai trường hợp.

Operations: Automatic or Manual Rebalancing?

Fully automatic⟷Fully manual
  • Automatic: system tự quyết khi nào move partition, không cần administrator.
  • Manual: assignment partition → node do administrator cấu hình tường minh.
  • Ở giữa: Couchbase, Riak, Voldemort tự sinh suggested assignment, admin phải commit mới có hiệu lực.

Automatic tiện (ít operational work) nhưng unpredictable: rebalancing đắt — reroute requests, move lượng lớn data — có thể làm quá tải network/nodes và ảnh hưởng requests khác.

Có human in the loop thì chậm hơn, nhưng tránh được operational surprises.

Đến giờ ta chỉ xét query đơn giản: read/write một key (cộng scatter/gather cho document-partitioned secondary indexes) — mức truy cập của hầu hết NoSQL distributed datastores.

MPP databases

Massively parallel processing relational databases (thường cho analytics) hỗ trợ query phức tạp hơn nhiều: nhiều join, filtering, grouping, aggregation.

MPP query optimizer chia query thành nhiều execution stages và partitions, phần lớn chạy song song trên các node. Query scan phần lớn dataset hưởng lợi nhiều nhất.

Summary

Partitioning cần thiết khi data quá lớn để lưu & xử lý trên một máy. Mục tiêu: chia data và query load đều trên nhiều máy, tránh hot spots.

🔑 Key range

Keys sorted; partition sở hữu một range min–max. Range queries hiệu quả, nhưng rủi ro hot spot khi truy cập keys gần nhau. Thường rebalance dynamically bằng split.

#️⃣ Hash

Mỗi partition sở hữu một range of hashes. Mất thứ tự keys → range query kém, nhưng load đều hơn. Thường dùng fixed number of partitions, move nguyên partition. Hybrid: compound key.

📇 Secondary indexes

Local (document-partitioned): write 1 partition, read scatter/gather. Global (term-partitioned): write nhiều partitions, read từ 1 partition.

🧭 Routing

Từ partition-aware load balancing đơn giản (ZooKeeper, gossip, routing tier) đến parallel query execution engines phức tạp.

Mỗi partition vận hành gần như độc lập — đó là điều cho phép scale ra nhiều máy. Nhưng operation ghi vào nhiều partitions thì khó lý giải: write vào partition này thành công, partition kia thất bại thì sao? → Chapter 7: Transactions.
