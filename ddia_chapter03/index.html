02

Index: read nhanh hơn, write chậm hơn

Một index là cấu trúc phụ, được derived từ primary data — giữ thêm metadata “bên lề”, đóng vai trò signpost giúp tìm data nhanh.

  • Thêm/xoá index không đổi nội dung database — chỉ ảnh hưởng performance của query.
  • Muốn search cùng data theo nhiều cách → có thể cần nhiều index trên các phần khác nhau.
  • Mỗi lần write, index cũng phải được update → overhead.
Đây là trade-off quan trọng: index chọn đúng giúp read nhanh, nhưng mọi index đều làm chậm write. Vì vậy database không tự index mọi thứ — developer/DBA chọn index dựa trên query patterns của app.

06

Biến ý tưởng đơn giản thành thực tế

Những vấn đề quan trọng trong một implementation thật:

🧾

File format

CSV không phải format tốt cho log. Dùng binary format: encode độ dài string (bytes) rồi tới raw string — không cần escaping.

🪦

Deleting records

Muốn xoá key thì append một deletion record đặc biệt — tombstone. Khi merge, tombstone báo bỏ mọi giá trị trước đó của key.

♻️

Crash recovery

Restart thì mất in-memory hash map. Đọc lại cả segment rất chậm → Bitcask lưu snapshot hash map của mỗi segment trên disk để load nhanh.

✂️ Partially written records

DB có thể crash giữa lúc đang append. File Bitcask có checksums để phát hiện và bỏ qua phần log bị corrupt.

🔒 Concurrency control

Write được append tuần tự nghiêm ngặt → thường chỉ có một writer thread. Segment là append-only và immutable → nhiều thread đọc đồng thời thoải mái.

TẠI SAO KHÔNG UPDATE IN PLACE?
🚀 Sequential writes

Append và merge segment là sequential write — nhanh hơn nhiều so với random write, đặc biệt trên magnetic spinning-disk; ở mức độ nào đó cũng tốt hơn trên SSD.

🧯 Concurrency & crash recovery đơn giản

Không lo trường hợp crash giữa lúc overwrite, để lại file nửa giá trị cũ nửa giá trị mới “dính” vào nhau.

🧹 Không bị fragmentation

Merge segment cũ tránh việc data file bị phân mảnh theo thời gian.

🧠 Phải vừa memory

📏 Range queries kém

Making an LSM-tree out of SSTables

Thuật toán trên chính là Log-Structured Merge-Tree (LSM-Tree) — Patrick O’Neil et al. (1996), dựa trên log-structured filesystems. Engine dựa trên nguyên lý merge & compact sorted files gọi là LSM storage engines.

LevelDBRocksDBCassandraHBaseGoogle BigtableLucene
  • LevelDB, RocksDB: key-value storage engine library để embed vào app khác (LevelDB có thể thay Bitcask trong Riak).
  • Cassandra, HBase: lấy cảm hứng từ paper Bigtable — nơi khai sinh thuật ngữ SSTable và memtable.

🔍 Lucene: full-text search

Engine của Elasticsearch và Solr. Key = một term (từ), value = danh sách ID document chứa từ đó (postings list). Mapping term → postings list nằm trong các file sorted kiểu SSTable, merge ở background.

15

Making B-trees reliable

Write cơ bản của B-tree là overwrite một page trên disk, page giữ nguyên vị trí — trái ngược hẳn với LSM-tree (chỉ append, không bao giờ sửa file tại chỗ).

  • HDD: di chuyển disk head, chờ platter quay tới đúng vị trí, ghi đè sector.
  • SSD: phức tạp hơn — phải erase & rewrite cả block lớn của chip.
WRITE-AHEAD LOG (WAL)

Còn gọi là redo log: file append-only, mọi thay đổi B-tree phải ghi vào đây trước khi áp vào page. Sau crash, dùng WAL để đưa B-tree về trạng thái consistent.

🔐 Latches

Nhiều thread truy cập cùng lúc → bảo vệ cấu trúc tree bằng latches (lightweight locks). Log-structured đơn giản hơn: merge ở background và atomically swap segment.

B-tree optimizations

B-tree đã tồn tại rất lâu nên có vô số tối ưu. Một vài ví dụ:

🐄

Copy-on-write

Thay vì overwrite + WAL, một số DB (như LMDB) ghi page sửa đổi ra vị trí mới, tạo version mới của các parent page trỏ tới đó. Hữu ích cả cho concurrency control (snapshot isolation).

✂️

Abbreviated keys

Page ở interior chỉ cần đủ thông tin làm boundary giữa các range → rút gọn key. Nhiều key/page hơn → branching factor cao hơn → ít level hơn. (Biến thể này đôi khi gọi là B+ tree.)

📐

Sequential leaf layout

Cố xếp leaf page tuần tự trên disk để range scan khỏi seek mỗi page — khó giữ khi tree lớn lên. LSM-tree rewrite cả segment khi merge nên dễ giữ key gần nhau hơn.

↔️ Sibling pointers

Mỗi leaf page có ref tới page anh em bên trái/phải → scan key theo thứ tự mà không phải quay lại parent.

Comparing: Advantages of LSM-trees

Rule of thumb: LSM-trees thường nhanh hơn cho writes · B-trees thường nhanh hơn cho reads — nhưng benchmark phải test với workload của chính bạn.

Write amplification

1 write vào database → nhiều write xuống disk trong suốt vòng đời data. Đặc biệt đáng lo với SSD (block chỉ overwrite được số lần hữu hạn).

📈 Write throughput cao hơn

Đôi khi write amplification thấp hơn, và ghi tuần tự các file SSTable gọn thay vì overwrite nhiều page — quan trọng nhất trên magnetic HDD.

🗜️ Nén tốt hơn, file nhỏ hơn

B-tree để lại khoảng trống do fragmentation (page split, row không vừa page). LSM không page-oriented, định kỳ rewrite SSTable → storage overhead thấp (nhất là leveled compaction).

💽 Trên SSD

Firmware SSD vốn dùng thuật toán log-structured để biến random write thành sequential, nhưng write amplification thấp và data gọn vẫn giúp phục vụ nhiều request hơn trong cùng I/O bandwidth.

Downsides of LSM-trees & điểm mạnh của B-trees

COMPACTION INTERFERENCE

Disk có tài nguyên hữu hạn → request có thể phải chờ compaction tốn kém. Throughput trung bình ít ảnh hưởng, nhưng high percentiles response time có thể rất cao; B-tree predictable hơn.

COMPACTION KHÔNG THEO KỊP

Disk write bandwidth chia giữa initial write và compaction threads. DB càng lớn, compaction càng tốn. Cấu hình không cẩn thận → segment chưa merge tăng mãi, hết disk, read chậm dần. SSTable engine thường không throttle write → cần monitoring.

B-TREE: MỖI KEY Ở ĐÚNG MỘT CHỖ

LSM có thể có nhiều bản copy của cùng key ở các segment. B-tree hấp dẫn cho strong transactional semantics: transaction isolation dùng locks on ranges of keys gắn trực tiếp vào tree (Chapter 7).

B-trees đã ăn sâu vào kiến trúc DB và sẽ không biến mất; log-structured index ngày càng phổ biến ở datastore mới. Không có rule nhanh — hãy test empirically.

Other Indexing Structures

Primary key vs secondary index

  • Primary key định danh duy nhất một row / document / vertex; record khác tham chiếu tới nó qua key.
  • Secondary index (CREATE INDEX) rất quan trọng cho join. Khác biệt: key không unique → value là list row ID (như postings list) hoặc nối thêm row ID vào key cho unique.
  • Cả B-tree lẫn log-structured index đều làm được secondary index.
Clustered & covering index tăng tốc read, nhưng tốn thêm storage, thêm overhead khi write, và DB phải cố gắng hơn để giữ transactional guarantees khi data bị duplicate.

Lưu value ở đâu trong index?

Full-text search & fuzzy indexes

Các index trước giả định data exact: query đúng giá trị key hoặc một range. Muốn tìm key tương tự (vd. từ viết sai) cần kỹ thuật khác — fuzzy querying.

  • Full-text search engine mở rộng query sang synonyms, bỏ qua biến thể ngữ pháp, tìm các từ gần nhau trong cùng document…
  • Lucene tìm được từ trong một edit distance nhất định (distance 1 = thêm, xoá hoặc thay một chữ).
  • In-memory index của Lucene là một finite state automaton trên các ký tự của key (giống trie), biến đổi được thành Levenshtein automaton.
  • Hướng khác: document classification, machine learning.

Keeping everything in memory

Mọi cấu trúc ở trên đều là câu trả lời cho giới hạn của disk. Ta chịu đựng disk vì: durable (mất điện không mất data) và rẻ hơn RAM mỗi GB. RAM ngày càng rẻ, nhiều dataset không lớn lắm → in-memory databases.

LoạiVí dụ
Cache onlyMemcached — mất data khi restart là chấp nhận được
RelationalVoltDB, MemSQL, Oracle TimesTen
Durable KVRAMCloud (log-structured cả trong memory lẫn disk)
Weak durabilityRedis, Couchbase — ghi disk asynchronously

Durability đạt được nhờ: battery-powered RAM, log thay đổi ra disk, snapshot định kỳ, hoặc replicate sang máy khác.

COUNTERINTUITIVE

Nhanh hơn không phải vì khỏi đọc disk — disk-based engine có đủ RAM thì OS cũng cache block rồi. Mà vì tránh được overhead encode in-memory data structure thành dạng ghi được ra disk.

🧩 Data model khó làm trên disk

Redis cung cấp interface kiểu database cho priority queues, sets… — implementation đơn giản vì mọi thứ nằm trong memory.

🔮 Anti-caching & NVM

Anti-caching: hết memory thì evict data least recently used ra disk, load lại khi cần — như virtual memory/swap nhưng ở granularity từng record (index vẫn phải vừa RAM). Non-volatile memory (NVM) có thể thay đổi thiết kế storage engine.

Transaction ban đầu gắn với giao dịch thương mại; nay chỉ một nhóm read/write tạo thành logical unit (không nhất thiết ACID). App tương tác → access pattern gọi là online transaction processing (OLTP). Analytics thì khác hẳn → online analytic processing (OLAP).

Storage engine chia làm hai nhóm lớn: tối ưu cho transaction processing (OLTP) và tối ưu cho analytics (OLAP).

📝 Log-structured school

Chỉ append và xoá file lỗi thời, không bao giờ update file đã ghi: Bitcask, SSTables, LSM-trees, LevelDB, Cassandra, HBase, Lucene. Biến random write thành sequential write → write throughput cao.

Disk = tập fixed-size pages được overwrite. B-trees là đại diện lớn nhất — có trong mọi relational DB lớn và nhiều nonrelational DB.

📊 Analytics

OLTP: user-facing, ít record/query, bottleneck là disk seek time. OLAP: ít query nhưng mỗi query scan hàng triệu row, bottleneck là disk bandwidth → column-oriented storage, compression.
